# Research: agent-tool verification policies — competitive

## Metadata
Date: 2026-09-24
Lane: competitive/vendor
Discussion: .agents/discussions/verification-levels.md

### Direct answer
No surveyed tool implements what our decision needs directly (graded verification tiers selected automatically by change content/paths, with caching of prior results, configurable per project). The closest is OpenHands's explicit **layered verification stack** (agent-level critic → repo-level code-review skill → repo-level QA agent), which is a genuine tier model but the tiers always all run, not selected by diff content. Everyone else does one of: (a) run one fixed command set project-wide after every edit (Aider, SWE-agent), (b) delegate "what to run" entirely to the project's own CI/test scripts discovered or named by the agent (Copilot coding agent, Amazon Q Developer, Sweep, Factory, Codex CLI via AGENTS.md), or (c) leave selection to human-authored config outside the agent (Claude Code hooks' path/glob matchers, Cursor Rules). Diff-aware/change-based test selection (skip suite on docs-only diffs, run only affected tests) exists as an established CI pattern (Nx affected, Vitest-affected, test-impact-analysis in various repos) but is not something any of the surveyed *agent* products do natively — it is bolted on by users via their own CI, not the agent's verification logic.

### Key findings (per tool, each with a link)
- **Aider** — two independent boolean toggles, `auto-lint` (default on) and `auto-test` (default off), each bound to a single project-configured command (`lint-cmd`, `test-cmd`) in `.aider.conf.yml`; lint runs after every edit, test only if enabled, and output is fed back to the model to self-correct. No distinction between doc-only and code edits, no tiers, no caching. [Options reference](https://aider.chat/docs/config/options.html), [YAML config file](https://aider.chat/docs/config/aider_conf.html)
- **OpenHands** — documents an explicit multi-layer "Verification Stack": Layer 1 is an in-loop critic model that scores a candidate solution and can stop/retry before push; Layer 2 is a repo-level code-review skill (10-scenario checklist) plus a QA agent that actually exercises the software (understand → setup → exercise → report). Repo-specific customization via `.agents/skills/custom-codereview-guide.md`, not automatic per-diff selection. Reports 58% reduction in mean time to merge; no cost data on the tiers themselves. [The Verification Stack (2026-05-06/06-22)](https://www.openhands.dev/blog/20260506-the-verification-stack), [AGENTS.md](https://github.com/OpenHands/OpenHands/blob/main/AGENTS.md)
- **SWE-agent** — fixed, always-on mechanism: a linter runs on every edit command and blocks the edit from landing if the result isn't syntactically valid; final verification is the canonical SWE-bench protocol, which applies a held-out fail-to-pass/pass-to-pass test patch only after the agent process exits. No tiering, no content-based selection — the check is identical for every task by construction of the benchmark harness. [SWE-agent (NeurIPS 2024)](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf), [Dissecting SWE-Bench leaderboards (2025)](https://arxiv.org/html/2506.17208v1)
- **Devin (Cognition)** — separates "should I even try this" from "did it work": a pre-run **Confidence Score** (correlated with merge success — green scores ~2x more likely to merge than red) can be requested from Linear/Jira without spending a session, letting teams triage before running the agent at all. Post-run, CI is necessary but explicitly documented as insufficient — "PRs from Devin should never be auto-merged, not even if CI checks all pass" — plus a separate Devin Review pass that labels findings Critical/Warning. This is the clearest *staged-gate* (pre-flight triage → CI → adversarial review → human) among the surveyed tools, though it's advisory scoring, not a mechanical tier selector. [Devin Review docs](https://docs.devin.ai/work-with-devin/devin-review), [Devin 2.1 blog](https://cognition.com/blog/devin-2-1)
- **Cursor (background agents)** — no built-in policy; verification is whatever the user puts in Cursor Rules (e.g. "run `npm test` before creating the PR") or a custom hook that loops the agent until tests pass. Explicitly documented pitfall: the loop only works if the test suite finishes before the next edit lands — letting the agent "finish the current thing" before a failure surfaces compounds on broken state. [Best practices for coding with agents](https://cursor.com/blog/agent-best-practices), [Keeping tests running in the background](https://www.thinkdifferent.blog/blog/cursor-keeping-tests-running-in-the-background-while-the-agent-edits-2026-08/)
- **GitHub Copilot coding agent** — runs the repo's own automated tests/linters "if they're present," and can auto-generate `copilot-instructions.md`/custom instructions (via a prompted comment on first PR) that tell it how to build/test/validate — so selection is whatever the repo already has wired, no agent-side tiering. A separate safety gate: PR workflows (CI) require explicit human approval to run at all, decoupling "agent's own verification" from "repo CI." [Copilot coding agent 101](https://github.blog/ai-and-ml/github-copilot/github-copilot-coding-agent-101-getting-started-with-agentic-workflows-on-github/), [Custom instructions changelog](https://github.blog/changelog/2025-08-06-copilot-coding-agent-automatically-generate-custom-instructions/)
- **Claude Code (hooks)** — the only surveyed tool with a documented, declarative path/content matcher for conditional checks: `PostToolUse` hooks take an `if` field using permission-rule syntax, e.g. `"Edit(*.ts)"` or `"Edit(src/**)"`, to run a command only for matching file edits — closest primitive to "select checks by the change's paths." Explicitly recommends against running the whole suite on every write ("slow feedback and high cost"); recommends scoping the linter to the changed package/directory instead. No native caching of prior results and no built-in notion of severity tiers — that logic is left to the hook script. [Hooks reference](https://code.claude.com/docs/en/hooks)
- **Codex CLI/cloud (OpenAI)** — verification policy lives entirely in the project's `AGENTS.md` ("run this test command," package-manager preference) with no agent-native selection logic; sandbox network-disabled flags are the one structural signal the harness gives back to tests (`CODEX_SANDBOX_NETWORK_DISABLED`) so a project's own test code can early-exit checks it knows the sandbox can't run — a form of environment-aware, not content-aware, gating. Codex explicitly separates "inspect/report" from committing: it reports prioritized findings without touching the working tree so risks can be triaged before commit/PR. [AGENTS.md (openai/codex)](https://github.com/openai/codex/blob/main/AGENTS.md), [Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)
- **Amazon Q Developer (agent)** — runs project-selected build/test commands "in real time" during generation via a devfile-launched sandboxed dev container, iterating on failures before presenting to the developer; selection is per-project devfile config, not per-diff. No tiering language, no caching documented. [Amazon Q Developer agent now runs builds and tests (AWS What's New, 2025-01)](https://aws.amazon.com/about-aws/whats-new/2025/01/amazon-q-developer-agent-builds-tests-validate-generated-code-real-time) — *note: >18 months old, may be superseded*
- **Sweep** — runs unit tests and autoformatters as part of PR generation, and explicitly supports CI/CD integration so "Sweep only marks a PR as ready once it passes your existing test suite" — verification is deferred to whatever CI the repo already runs, agent adds a sandboxed pre-check pass. No content-based selection or tiers documented. [Sweep AI overview](https://www.onegen.ai/project/sweep-ai-automated-github-issue-resolution-and-pull-request-generation/) — thin/marketing-grade sourcing, treat as low-confidence
- **Factory (droids)** — documents a hard gate for its own TDD/spec workflow: "execute the exact commands specified by the spec/orchestrator (tests, lint, type, optional coverage)... confirm zero exit for each command before stopping" — i.e. verification commands are specified per work item by the orchestrating spec, not chosen dynamically by the droid from the diff. Separately ships a code-review droid that flags risk and lists follow-ups pre-merge. [Droid Control](https://docs.factory.ai/software-factory/droid-control), [Automated Code Review](https://docs.factory.ai/software-factory/code-review-ci)
- **CrewAI / LangGraph / MetaGPT** — no documented verification *policy* comparable to the above. CrewAI as of v1.15.20 (2026-09-04) explicitly **removed** built-in sandboxed code execution, pushing verification entirely to user-wired steps; MetaGPT's SOP pipeline produces PRD/design/code artifacts but sourcing found no documented test-gating policy distinct from "generate tests as part of the pipeline." Treat this row as a gap, not a negative finding — these are frameworks, not opinionated products, so verification is a template choice left to the implementer. [CrewAI vs LangGraph benchmark methodology](https://markaicode.com/benchmarks/multi-agent-benchmark/)

### negative: (contradicting evidence, gaps, undocumented behaviour)
- No surveyed agent product documents automatic **change-type classification** (docs/comment-only vs code) gating which checks run — Claude Code hooks come closest but require the user to write the path-glob rule by hand.
- No surveyed agent documents **caching of prior verification results** across turns/edits (e.g. skip re-running a check if the relevant files are unchanged since last pass) — every tool either reruns the fixed command set or defers entirely to external CI, which has its own (unrelated to the agent) caching.
- "Grading into levels" is real only at OpenHands (agent-critic vs repo-review vs QA-exercise) and arguably Devin (pre-flight confidence vs CI vs adversarial review vs human) — but in both cases the tiers are fixed pipeline stages, not something selected per-change; none of the sourcing shows a tool choosing "run tier 1 only" vs "run tier 1+2+3" based on diff size/risk.
- CrewAI's removal of built-in execution (Sept 2026) is a **regression** in agent-native verification for that framework — worth flagging since it's very recent and could be missed by anyone assuming CrewAI still sandboxes code.
- Sourcing quality is uneven: Sweep and Amazon Q findings lean on marketing/blog pages rather than primary docs; Amazon Q's core "runs builds and tests in real time" citation is from January 2025 (>18 months old) and may not reflect the current agent.
- Diff-aware/affected-test selection (Nx affected, vitest-affected, TIA) is a mature, separate ecosystem pattern but is not something any surveyed *agent* implements internally — it would have to be adopted from the CI/build-tooling world, not copied from a competitor agent.

### leads: (one line each: lane name — reason)
- prior-art/build-tooling lane — Nx affected / Bazel test selection / vitest-affected show a working diff→test-graph selection mechanism worth evaluating for the "select by paths/content" half of the decision, since no agent vendor has solved it.
- architecture/mechanism lane — OpenHands's fixed 3-layer stack (critic → review → QA-exercise) is the nearest existing shape for our "levels" concept; worth deciding whether our levels are fixed-always-run (like OpenHands) or diff-selected (novel, unprecedented among peers).
- security/gating lane — Devin's pre-flight confidence score (score before spending a run) is a distinct idea from post-hoc test selection: worth deciding whether our toolkit wants a pre-plan risk/cost gate in addition to a post-edit verification tier.
