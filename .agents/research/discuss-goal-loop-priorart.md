# Research: long-horizon agent loop prior art

## Metadata

**Date:** 2026-09-22
**Domain:** cli
**Triggered by:** pre-plan discussion on replacing hand-written `/goal` prompts (`.tmp/examples/loops/*.md`) with a reusable, less error-prone mechanism for chaining hex-architect → hex-plan → hex-execute → hex-review → hex-finalize autonomously
**Expires:** 2027-03-22

## Direct Answer

Claude Code ships three distinct persistence/loop primitives (`/goal`, `/loop`, Stop hooks) plus cloud `Routines` — each with different persistence, stop-condition, and portability properties (details below). Prior-art "Ralph Wiggum"-style loops solve the same problem external to any harness, with well-documented failure modes. Neither shape (a) pasted mega-prompt vs (b) skill+small-goal-file is settled by the evidence; both have real tradeoffs, given below without a pick.

## Key Findings

### 1. Claude Code native primitives

**`/goal <condition>`** ([code.claude.com/docs/en/goal](https://code.claude.com/docs/en/goal))
- Sets a completion condition (≤4,000 chars). One goal active per session; setting a new one replaces the old.
- Mechanism: `/goal` is literally "a wrapper around a session-scoped prompt-based Stop hook." After every turn, the condition + conversation-so-far is sent to the configured small-fast model (Haiku by default) which returns **not-yet-met / met / impossible** + a short reason. Not-yet-met → Claude starts another turn using the reason as guidance. Met → goal clears, "achieved" recorded in transcript. Impossible → goal clears, "failed" recorded — no manual clear needed.
- The evaluator **does not run commands or read files independently** — it only judges what Claude already surfaced in the conversation. Docs explicitly recommend writing conditions with a stated check ("`npm test` exits 0"), not vague outcomes.
- **Persistence**: thread/session-scoped. Survives `--continue`, `--resume` (session ID, name, or transcript path), and the session picker (all routes as of v2.1.239; before that, the picker route didn't restore it). Survives context compaction — auto-compaction runs, goal condition carries over. On resume, condition text is kept but turn count / timer / token-spend baseline reset. An *achieved* or *cleared* goal is not restored.
- **Does not persist to a file** — it's an in-conversation/session construct, not a filesystem artifact. `/clear` (new conversation) wipes it.
- **Stop condition / runaway guard**: if Claude answers the evaluator several turns in a row with no tool use (i.e., spinning without progress), Claude Code force-stops the loop, warns, and returns control — goal stays set, resumes on your next prompt.
- **Error handling**: 4 classes of "unrecoverable" errors (auth failure Claude Code manages itself, exhausted credits, context overflow auto-compact couldn't clear, model unavailable) **clear the goal** and require `/goal <condition>` again. Other errors (overload, dropped connection, rate limit, usage-limit) **retry automatically** (up to 3x) then **pause** — goal stays set, resumes when you send a message or when a usage-limit-wait resolves.
- **Background work handling**: if a subagent or background shell is still running at turn-end, evaluation is deferred to the next turn with nothing running. After 30 min (default, env-tunable via `CLAUDE_CODE_GOAL_CHECKIN_MINUTES`) of the goal waiting on background work, a **check-in** fires: Claude Code lists running tasks and asks Claude to read output, keep waiting, or fix/stop stuck ones. Backoff doubles each check-in up to 4x the base interval. In interactive sessions, up to 3 check-ins can fire while idle (no new prompt from you) before check-ins pause until you send something — this directly targets the "idle subagent" failure mode named in the loop examples.
- **Skill invocation in the condition text**: **not explicitly documented**. The docs say "Setting a goal starts a turn immediately, with the condition itself as the directive," implying it is sent as an ordinary user turn — by extension a condition beginning `/hex-plan high "..."` would presumably be parsed as a slash-command the same way typed input is, but the `/goal` doc page does not state this, unlike the `/loop` page which explicitly documents skill-as-prompt (`/loop 20m /review-pr 1234`) and even enumerates what does *not* execute (built-ins like `/permissions`, `disable-model-invocation: true` skills, skill-overrides, MCP prompts — those "reach Claude as plain text instead of executing"). This is a genuine gap between what the example prompts assume and what's confirmed in docs.
- Requires the hooks/workspace-trust gate (same as any Stop hook); unavailable if `disableAllHooks` or `allowManagedHooksOnly` is set.
- Non-interactive: works with `-p`, desktop app, Remote Control; `-p` runs the loop to completion in one invocation, only delivers check-ins at turn-end (no idle check-ins possible without an open interactive loop).

**`/loop [interval] [prompt]`** ([code.claude.com/docs/en/scheduled-tasks](https://code.claude.com/docs/en/scheduled-tasks))
- Different shape: re-runs a prompt on an interval rather than iterating toward a condition. Three modes: fixed interval (`/loop 5m ...`), Claude-chosen dynamic interval (prompt only, 1min–1hr adaptive), or built-in maintenance prompt (bare `/loop`, or your own `.claude/loop.md` / `~/.claude/loop.md`, ≤25,000 bytes, project overrides user).
- Explicitly documents piping a skill as the prompt (`/loop 20m /review-pr 1234`), and documents exactly which skill/command forms are inert text vs. executed.
- Session-scoped like `/goal`; restored on `--resume`/`--continue` **except** dynamically-paced loops (must re-issue `/loop`) and background Bash/monitor tasks (never restored). 7-day hard expiry on recurring tasks (self-deletes after one final fire) — a built-in bound against forgotten infinite loops. Max 50 scheduled tasks per session.
- Self-paced loop stop conditions: `Esc` (interactive) clears pending wakeup; Claude itself can call `ScheduleWakeup(stop: true)`; if an iteration ends without rescheduling or stopping, one 20-min fallback wakeup fires, then the loop ends if that one also doesn't reschedule.
- Comparison table in docs: `/goal` next-turn trigger = "previous turn finishes, idle check-in, or automatic retry due"; `/loop` = "time interval elapses"; Stop hook = "previous turn finishes" (identical trigger to `/goal`, since `/goal` *is* a Stop hook).

**Stop hooks (prompt-based)** ([code.claude.com/docs/en/hooks-guide#prompt-based-hooks](https://code.claude.com/docs/en/hooks-guide))
- The general mechanism `/goal` is built on. Configured in settings files (project/user scope), applies to every session in that scope (not just one), can run either a script (deterministic check) or a prompt (model-evaluated, same shape as `/goal`'s evaluator). This is the path to **custom evaluation logic** beyond what `/goal`'s built-in evaluator does — e.g., a Stop hook script that actually runs the test suite / lints the PR / checks CI status server-side rather than trusting what's in the transcript.

**`ScheduleWakeup` tool** — used internally by self-paced `/loop`; lets Claude say "wake me in N with this prompt" and go idle. Confirmed via docs as the mechanism, not separately documented as a general-purpose tool for hand-authored loops outside `/loop`.

**Background agents / Agent View** (`claude agents`, `/bg`, `claude --bg`) — session-level parallelism, not goal-persistence. Each background session gets its own git worktree (under `.claude/worktrees/`), its own subscription-quota draw (costs are additive/multiplicative across parallel agents — flagged as a real cost-blowup vector), a supervisor process that stops idle processes after ~1hr (state saved, resumes on next attach) and auto-restarts on unexpected exit. Idle/stuck detection surfaces as `blocked` (needs you) vs `done` (finished, waiting for next prompt) vs `working`. Documented stuck-state causes: permission/dialog prompts that can't be satisfied unattended (e.g. `/install-github-app`), machine-sleep mid-response (auto-resumes from where interrupted), post-shutdown zombie states (48hr `failed`→`stopped` transition, `claude respawn <id>` if transcript is gone).

**Routines** (cloud, research preview) ([code.claude.com/docs/en/routines](https://code.claude.com/docs/en/routines)) — the only Claude Code primitive that runs independent of any open session/machine. A routine = saved prompt + repos + connectors + trigger(s) (schedule/API/GitHub event). Fresh clone per run (no local file access), runs fully autonomously with **no permission-mode picker** — nothing stops for approval except some artifact actions. Min schedule interval 1hr. Daily run cap per account; one-off runs exempt. Fire-time payload text arrives wrapped as explicitly-untrusted (`<routine-fire-payload>`) unless the saved prompt opts in to reading it — a prompt-injection mitigation worth noting given the example prompts' `/goal` text embeds live GitHub issue URLs as context. Not really built for the arcana use case (needs local hex worktrees, `.agents/` state, multi-hour interactive iteration) but documents the ceiling of "runs with the machine off."

### 2. Prior-art: Ralph Wiggum loop and adjacent patterns

- **Origin**: named/popularized by Geoffrey Huntley, mid-2025 (~July). Core mechanism: an external script starts the CLI agent with a prompt, and as soon as the agent process exits, immediately restarts it — deliberately **fresh context each iteration**, with state (what's done, what's next) persisted externally in files (a PRD/spec, a task list, a progress log) rather than in conversation memory. [codecentric write-up](https://www.codecentric.de/en/knowledge-hub/blog/the-ralph-wiggum-loop-autonomous-code-generation-with-a-fresh-context), [Medium](https://vibecode.medium.com/ralph-running-ai-coding-agents-in-a-loop-seriously-f8503a219da6), [ralphwiggum.org](https://ralphwiggum.org/), [ralph-wiggum.ai](https://ralph-wiggum.ai/), [aihero.dev tips](https://www.aihero.dev/tips-for-ai-coding-with-ralph-wiggum).
- **Phase structure**: commonly broken into plan → implement → test → verify → PR-review, each an independent agent invocation with a checkpoint between — directly analogous to the arcana hex-architect/plan/execute/review/finalize chain, but done via external orchestration rather than an in-session command.
- **Portability claim**: the pattern itself is described as harness-agnostic — "works with Claude Code, OpenAI Codex CLI, Gemini CLI, OpenCode, or any CLI-based coding agent" ([ishir.com](https://www.ishir.com/blog/312751/ralph-wiggum-and-ai-coding-loops-from-springfield-to-real-world-software-automation.htm)) — because it's just a shell loop around a CLI invocation plus files on disk for state, not a harness feature.
- **Documented failure modes** ([futureagi.com — 6 production failure modes](https://futureagi.com/blog/ralph-loop-production-failure-modes/), [ralphloop.sh](https://ralphloop.sh/blog/ralph-loop-failure-modes), [Dominic Böttger — Spec Kit + Ralph](https://dominic-boettger.com/blog/speckit-ralph-loop-fresh-context-ai-development/)):
  - Search false negatives, placeholder/stub code left behind, non-deterministic retrieval across iterations, context-exhaustion quality clipping, compounding-broken-builds (a bad iteration's breakage compounds into the next), multi-agent collisions when parallelized.
  - General framing: "it forgets, it overspends, it chases a bad goal, it lies to itself about success, and it can break things it touches."
  - Context exhaustion: quality degrades non-linearly past ~60–70% context fill (the "dumb zone") — argues for the fresh-context-per-iteration design itself as the mitigation, at the cost of having to re-derive/re-read state each time from the persisted files.
  - Cost: "a fifty-iteration loop on a medium codebase typically runs $50–100+ in API credits" — iteration/time caps are the documented mitigation (echoed in the arcana examples' "max 2-5 turns" refinement-loop caps).
  - Goal drift: "if your spec is vague about what 'done' means, the agent will interpret it differently each loop" → drift, scope creep, contradictory iterations. "Plan staleness" when the plan file isn't regenerated as reality changes.
- **Escalation/watchdog patterns from smaller open-source projects** (lower-confidence, single-repo sources, treat as illustrative not authoritative): a `tick`-based state machine distinguishing `working`/`blocked`/`idle`, where blocked agents "notify once and then escalate on a timer," and an agent that "vanished while its pane is still up is restarted exactly once" ([tonoid/agent-loop](https://github.com/tonoid/agent-loop)); a documented gap where "a pane that declares running subagents and then stalls is invisible to every watchdog" unless the watchdog treats declared-subagent-running the same as declared-working ([giuseppecrj/pi-herdr-agents #40](https://github.com/giuseppecrj/pi-herdr-agents/issues/40)); "a dispatched agent going idle with a dirty worktree is silent" unless idle notifications carry a dirty/unpushed flag; a stated motivation that "models end turns at the first natural pause, leaving multi-step objectives half-finished" ([suneel944/agent-parley #336](https://github.com/suneel944/agent-parley/issues/336)). These read as the same idle-subagent problem the arcana example prompts hand-write a mitigation for ("wake-up routines that re-check state every 5 min, and pull any subagent that goes idle without reporting") — Claude Code's own check-in mechanism (above) covers the *session-level* version of this natively; nothing found natively covers a sub-orchestrator's *own* spawned subagents going idle (that remains the caller's responsibility per this project's existing memory note "Subagent results route to top session").

### 3. Shape (a) pasted-prompt vs (b) skill+small-goal-file

No source directly adjudicates this pair; evidence is indirect, gathered from how the platforms themselves are built and from Ralph-loop practice:

**For (a) — reusable prompt template, pasted/typed each time:**
- Matches how `/goal` is designed to be used: a self-contained condition string, ≤4,000 chars, is the whole mechanism — no separate file layer is native to it.
- Routines explicitly warn the *opposite* of file-based state: "the prompt must be self-contained and explicit... since the routine runs autonomously" and fire-payload text is treated as untrusted unless the prompt opts in — reinforcing that the authoritative instructions are expected to live in the prompt/condition text itself, not fetched from a file the agent must remember to open.
- Portable across harnesses in the Ralph-loop framing precisely because it's "just a prompt" — no harness-specific file convention to port.

**For (b) — invariant protocol in a persistent skill/instruction file + small per-run goal file:**
- `/loop`'s `loop.md` convention (`.claude/loop.md` project-level, `~/.claude/loop.md` user-level, project wins) is Claude Code's own precedent for exactly this split: invariant behavior in a committed file, edits take effect on the *next* iteration without restarting the loop (a concrete advantage a pasted-each-time prompt cannot offer mid-run).
- Ralph-loop practice's fresh-context-per-iteration design *requires* externalized state (PRD/spec/task-list files) since conversation memory is deliberately discarded — the invariant-protocol-in-a-file shape is closer to how the pattern is actually implemented in the wild, not just documented.
- Cross-harness precedent for *instruction* files (not goal files specifically): every major CLI agent already reads a project-level instruction file (Codex CLI → `AGENTS.md`, Claude Code → `CLAUDE.md`, Gemini CLI → `GEMINI.md`, Copilot → `.github/copilot-instructions.md`, Windsurf → `.windsurfrules`) — described as "a fragmented landscape" for teams running multiple tools ([codex.danielvaughan.com](https://codex.danielvaughan.com/2026/05/27/agent-instruction-files-agents-md-claude-md-cross-tool-portability-codex-cli/)). A protocol-in-a-file approach inherits this fragmentation if it must be portable to Codex/Copilot/OpenCode; a pasted-prompt approach sidesteps the file-naming problem entirely but must be retyped/reconstructed per harness anyway since slash-command syntax (`/hex-plan`, `/goal`) is Claude-Code-specific regardless.
- Codex has a comparable persisted-goal primitive: "Codex's changelog indicates version 0.128.0 added persisted `/goal` workflows with app-server APIs, model tools, runtime continuation, and TUI controls to create, pause, resume, and clear goals" ([developersdigest.tech](https://www.developersdigest.tech/blog/codex-goal-vs-claude-managed-outcomes-practical-differences)) — suggesting the *concept* (not the exact mechanism) is portable, but each harness's goal primitive is independently implemented, so a goal condition string written for Claude Code's evaluator is not guaranteed to behave identically under Codex's.
- An open GitHub feature request, [anthropics/claude-code#56085](https://github.com/anthropics/claude-code/issues/56085), explicitly frames `/goal` as "parity with Codex CLI 0.128.0" — i.e., the two evolved convergently but not from a shared spec, which is evidence *against* assuming portable semantics for goal-condition text across harnesses even where both have a `/goal`-shaped feature.

## negative:

- Whether `/goal <text>` executes an embedded slash-command/skill invocation (e.g. `/goal /hex-plan high "..."`) the way `/loop`'s prompt argument explicitly does, is **not confirmed** in official docs — the `/goal` page is silent on this while the `/loop` page explicitly enumerates it. Treat as unverified if the design depends on it; a Stop-hook-only (custom prompt-based hook, not `/goal`) approach could deterministically avoid this ambiguity since you control the hook's own prompt-construction logic.
- `/goal`'s evaluator "does not run commands or read files independently" — it only judges the transcript. Any design that leans on `/goal` for a large, multi-day chain risks the evaluator being fooled by transcript text that *claims* success without independent verification; the docs' own example ("`npm test` exits 0" must actually appear in the transcript) shows this is a known sharp edge, not a hidden one.
- Idle-check-in coverage is capped: only 3 idle check-ins fire between prompts before Claude Code pauses check-ins until you send something — so a `/goal` loop left fully unattended for many hours (the arcana examples' actual use case) will stop self-nudging itself well before a multi-day horizon completes, unless something external (a human, a cron `/loop`, or a Routine) re-primes it.
- Session-scoped `/loop` and `/goal` state is not restored across `/clear` (new conversation) at all, and dynamically-paced `/loop`s are not restored even across `--resume` — any design assuming seamless resume-after-compaction needs `/goal` specifically (which does survive compaction and most resume routes), not `/loop`.
- Cost claims ("$50-100 per 50-iteration loop") come from blog-level sources on a "medium codebase," not vendor-published numbers — treat as an order-of-magnitude anecdote, not a budget figure.
- Several watchdog/escalation sources (tonoid/agent-loop, pi-herdr-agents, agent-parley, agyloop) are small/single-maintainer GitHub repos describing their *own* home-grown orchestration layers, not independently validated patterns or widely-adopted frameworks — cite as illustrative of the problem shape, not as proven solutions.

## leads:

- **Custom Stop-hook script (non-`/goal`) for deterministic done-checks** — since `/goal`'s evaluator only reads the transcript, a scripted Stop hook that actually shells out to `task verify` / `gh pr checks` / CI status could close the "evaluator judges from transcript only" gap; worth a follow-up read of `/docs/en/hooks-guide#prompt-based-hooks` and the deterministic (non-prompt) Stop hook variant.
- **Routines as the outer wrapper for true multi-day/unattended runs** — since `/goal`'s idle-check-in cap (3x) means it can't truly run unattended for days inside one interactive session, a Routine (schedule or GitHub-event triggered) that re-fires a `/goal`-setting prompt into a fresh cloud session on a cadence might be the actual mechanism for the "multi-day-scale" framing in the topic — worth checking whether Routines can target an existing worktree/branch rather than always cloning fresh.
- **Spec Kit + Ralph loop combination** ([dominic-boettger.com](https://dominic-boettger.com/blog/speckit-ralph-loop-fresh-context-ai-development/)) — a named pattern combining GitHub's Spec Kit (spec-driven scaffolding) with Ralph-style fresh-context iteration specifically to solve context exhaustion on large features; close cousin to arcana's own spec/plan/ADR file conventions (`.agents/specs/`, `.agents/plans/`, `.agents/adrs/`) and worth comparing directly against hex's existing fold-back design.
- **`ScheduleWakeup`/Monitor tool as a lower-level primitive than `/loop`** — docs note Claude "may use [Monitor] directly when you ask for a dynamic `/loop` schedule... avoids polling altogether and is often more token-efficient" — could be a cheaper substitute for a hand-rolled "check every 5 min" wake-up routine than either `/goal` idle-check-ins or a cron `/loop`.
- **Prompt-injection framing on Routine fire-payloads** (`<routine-fire-payload>` wrapping, "not live user input and can't act as approval or consent") — relevant precedent if any future design pipes live GitHub issue/PR text into an autonomous goal condition, as several of the example loop prompts already do (raw issue URLs as "Context").
