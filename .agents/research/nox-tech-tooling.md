# Research: OpenCode programmatic surface, zipapp packaging, reproducible builds, stdlib process-control sufficiency

## Metadata
- Date: 2026-08-31
- Axis: technology / tooling
- Question: For `nox` (zero-dependency Python zipapp that drives one headless AI coding harness to adversarially review another, v1 targeting Claude Code + OpenCode) — what is OpenCode's real programmatic surface (the uncovered gap vs. prior Claude Code/Codex/Copilot/Cursor research), and does the stdlib (`subprocess`, `json`, `tomllib`, `shutil`, `threading`, `signal`, `dataclasses`, `selectors`) actually cover long-running-child control, incremental non-deadlocking stdout reads, timeouts, and SIGTERM→SIGKILL escalation — plus zipapp/reproducible-build packaging constraints?
- Sources: live probe of the real `opencode` 1.18.22 binary via `ocx package exec ocx.sh/anomalyco/opencode:1.18.22 -- opencode <cmd> --help` (2026-08-31, this session, non-interactive, no auth performed, no repo modification); opencode.ai/docs/{cli,config,permissions,agents,server} (fetched 2026-08-31); GitHub anomalyco/opencode issues #5423, #5238 (fetched 2026-08-31); docs.python.org/3/library/{zipapp,subprocess,selectors} (fetched 2026-08-31); reproducible-builds.org/docs/{source-date-epoch,archives,timestamps} and drivendataorg/repro-zipfile (fetched 2026-08-31); python/cpython issue #121735 and python/importlib_resources issue #44 (fetched 2026-08-31).
- Expires: 2027-02-28 (OpenCode's CLI moves fast pre-1.0-contract per its own docs lagging the binary — see negatives; re-verify flags against a current `opencode --help` before relying on exact argv past this date. CPython stdlib facts (zipapp, subprocess, selectors) do not expire on this horizon.)

## Priority 1 — OpenCode's programmatic surface (verified against the real 1.18.22 binary)

**One-shot / non-interactive invocation.** `opencode run [message..]` is the headless entry point — no `-p` flag exists (that name is stale/confused with the server password flag `-p/--password`); the message is a positional array. Exact argv observed:

```
opencode run --format json --model <provider>/<model> [--agent <name>] [--auto] [-f <file>]... "<message>"
```

Confirmed live: `opencode run --format json --model doesnotexist/doesnotexist "test"` (no credentials configured) exited **1** and printed one JSON line to stdout:
```json
{"type":"error","timestamp":1788205196489,"sessionID":"ses_...","error":{"name":"UnknownError","data":{"message":"Unexpected server error. Check server logs for details.","ref":"err_..."}}}
```
This is a load-bearing finding: even a hard failure surfaces as a **structured JSON event on stdout**, not just a bare exit code or stderr prose — so a parser that only branches on exit code will miss the error taxonomy, and one that only reads stdout-as-events will need an `"type":"error"` case, not just `"type":"message"`/`"type":"tool"` etc. `UnknownError`/`err_<hex>` is an opaque wrapper here; distinct provider-side codes (not-authenticated vs. rate-limited) were **not observed** in this probe because no real provider was configured (see negatives).

**Machine-readable output.** `--format json` ("raw JSON events") vs. default ("formatted" prose) — confirmed via `opencode run --help`. This is a real streaming-events mode (session/message/tool-call/error events), not a single final blob — confirmed structurally by the single-line JSON-per-event shape above and corroborated by opencode.ai/docs/cli. This is usable as a liveness/heartbeat signal: each JSON line on stdout is itself the heartbeat (equivalent to Claude Code's `stream-json`).

**Permission / tool-restriction flags.** No CLI flag equivalent to Claude Code's `--permission-mode`/`--allowedTools`. Restriction is **config-file-driven**, not argv-driven:
- Global `permission` key in `opencode.json`/`opencode.jsonc`, one of `"allow"|"ask"|"deny"` per tool-class (`read`, `edit`, `glob`, `grep`, `bash`, `task`, `skill`, `lsp`, `question`, `webfetch`, `websearch`, `external_directory`, `doom_loop`), with glob/wildcard pattern matching for bash (`"git *": "allow"`, `"rm *": "deny"`).
- Per-agent `tools: {write: false, edit: false}` overrides inside `agent.<name>` config.
- Two **built-in restricted agents** exist and are directly usable as the "review, don't touch" mode nox needs: **`explore`** ("fast, read-only agent for exploring codebases. Cannot modify files") and **`plan`** (edit/bash default to `"ask"`, i.e. gated not silently blocked). Select with `opencode run --agent explore ...`.
- `--auto` ("auto-approve permissions that are not explicitly denied (dangerous!)") is the closest thing to a blanket non-interactive flag; it still requires explicit `deny` rules to guarantee zero mutation — there is **no single flag that guarantees read-only** the way `--agent explore` does structurally. For a headless reviewer, `--agent explore` (or `--agent plan` with `--auto` off) is the safer primitive than composing `permission` overrides.

**Model/provider selection and credentials.** BYOK/multi-provider, selected via `-m/--model provider/model` on `run`, or `opencode models [provider]` to enumerate what's resolvable (backed by models.dev). Credentials live in `~/.local/share/opencode/auth.json` (mode 0600) — confirmed live via `opencode providers list`, which on this machine reported `0 credentials` plus one environment-variable-backed provider (`GitHub Copilot` via `GITHUB_TOKEN`) without prompting or blocking, i.e. `providers list` is safe to shell out to as a preflight "is anything configured" check. Override paths: `OPENCODE_AUTH_JSON` env var relocates the credentials file; `OPENCODE_<PROVIDER>_APIKEY` env vars inject a key without touching auth.json at all (per GitHub issue #5423 discussion) — that's the cleaner injection point for a nox harness that wants to stay out of the user's global credential store.

**Config file format and resolution.** `opencode.json` / `opencode.jsonc` (JSONC, i.e. JSON-with-comments — not TOML). Documented merge order (opencode.ai/docs/config, 2026-08-31 fetch): remote `.well-known/opencode` → global `~/.config/opencode/opencode.json` → `OPENCODE_CONFIG` path → project `opencode.json` → `.opencode/` dirs → `OPENCODE_CONFIG_CONTENT` env-inline → managed/MDM tiers. Project discovery walks **upward to the nearest Git repository**, same shape as Claude Code's `.claude` discovery. `opencode debug config` (confirmed present via `opencode debug --help`) dumps the fully-resolved merged config — useful for nox to snapshot what OpenCode will actually do before invoking `run`. `opencode debug paths` (run live, exit 0) confirms the full path set: `data=~/.local/share/opencode`, `config=~/.config/opencode`, `cache=~/.cache/opencode`, `state=~/.local/state/opencode`, `log` under data, `tmp=/tmp/opencode`.

**Exit-code semantics.** Only one class was actually exercised (config/provider-resolution failure → exit 1, JSON error event on stdout). OpenCode's docs do not enumerate a distinct exit-code table for auth-missing vs. rate-limited vs. ran-but-failed — **this is a negative finding**: exit codes are coarse (0 success, non-zero failure), and the *kind* of failure lives in the JSON event stream's `error.name`/`error.data`, not in `$?`. A nox harness must parse the JSON stream to distinguish "not authenticated" from "rate limited," not branch on exit code alone. This mirrors what prior research found for Claude Code's `--output-format stream-json`, so the parsing strategy (JSON-event-driven classification, exit code only as a coarse success/fail gate) generalizes across both v1 targets.

**Server/headless mode.** `opencode serve` starts a headless HTTP server (`--port`, default 0 = random; `--hostname`, default `127.0.0.1`; `--mdns`; `--cors`). Auth via HTTP basic, `OPENCODE_SERVER_PASSWORD` env var (username defaults to `opencode`, overridable via `OPENCODE_SERVER_USERNAME`). Full OpenAPI 3.1 spec self-served at `http://<host>:<port>/doc`. SSE event stream at `/event` (and `/global/event`), beginning with a `server.connected` message. `opencode run --attach <url>` lets a one-shot invocation reuse an already-warm server (documented rationale: avoid MCP cold-boot cost per run) — relevant to nox only if it needs to fire many review passes cheaply; for a single adversarial-review invocation the plain `opencode run` path is simpler and avoids managing a second long-lived process.

**Version/stability posture.** No documented CLI compatibility contract was found. opencode.ai's own docs are reported (independently, by a third-party guide fetched 2026-08-31) to sometimes trail the actual binary — consistent with what this probe found (`--help` output for `run`/`serve`/`agent`/`providers`/`mcp`/`debug`/`models` all came from the live binary, not docs prose, precisely because the docs are not trustworthy as an argv source). **Recommendation for nox: parse `--help` output or pin an exact OpenCode version per grim/zipapp release rather than trusting flag names to stay stable across minor versions**, the same posture prior research presumably already took for Claude Code.

### Negative (Priority 1)
- Did not test a real provider (no auth performed, per instructions), so distinct exit-code/error-name behavior for "not authenticated" vs. "rate limited" vs. "ran but tool call failed" is **unverified** — only "provider unresolvable" was observed. Recommend a follow-up smoke test with a real (test) API key before nox's error-classification logic ships.
- Did not start `opencode serve` and hit `/event` live (out of scope per instructions to avoid any interactive/long-running session); SSE shape is doc-sourced, not probed.
- `opencode --pure` ("run without external plugins") appeared in every subcommand's help but its exact scope (does it also suppress MCP servers configured in `opencode.json`?) was not verified against docs or live behavior — worth checking before relying on it to reduce headless review's blast radius.

## Priority 2 — zipapp packaging constraints (CPython docs, 2026-08-31)

- **Shebang**: on POSIX, `zipapp -p "/usr/bin/env python3"` writes a real `#!` line and sets the executable bit — the OS kernel interprets it, so `./nox.pyz` runs directly. On Windows there is no OS-level shebang; the **py launcher** reads the same `#!` line and the `.pyz`/`.pyzw` extensions are registered against Python at install time, so double-click/`nox.pyz` from a shell both work if `py.exe` is on PATH — no shebang means Windows falls back to needing `python nox.pyz` explicitly.
- **Bytecode/`__pycache__`**: not addressed by the `zipapp` docs at all (confirmed absence, not merely unread) — `python -m zipapp` zips the source tree as given; it does not itself compile bytecode or emit `__pycache__` entries. Whatever is in the source directory when `zipapp` runs is what ships, so a CI step must not leave stale `__pycache__` in the staging dir or it becomes part of the archive (affecting reproducibility, see Priority 3).
- **Paths with spaces**: not addressed by the docs. Not independently verified in this pass; treat as **unverified**, not confirmed-safe — zipimport reads the archive by path at Python-interpreter level (not shell-parsed), so it's very likely fine, but nox's own CI/build scripts should still quote paths defensively regardless.
- **`importlib.resources` inside a zipapp**: works, with one sharp edge confirmed via python/cpython#121735 and python/importlib_resources#44 — **`importlib.resources.files()` called with no argument** fails to resolve inside a `.pyz` (works fine unzipped/installed normally); calling it **with an explicit package name**, `importlib.resources.files("nox")`, works in both contexts. This is a real, cite-able gotcha nox must apply: never call the bare/no-arg form when reading bundled data (e.g. prompt templates, the JSON-schema files nox would ship) from inside the `.pyz`.
- **Stdlib-only zipapp compatibility**: no incompatibility found for pure-stdlib code — zipapp's whole design point is that it just zips a source tree and CPython's `zipimport` loads modules straight out of the archive; the only known landmine is the `importlib.resources` no-arg case above, not a stdlib-vs-zipapp conflict in general.

### Negative (Priority 2)
- Spaces-in-archive-path behavior is a documentation gap, not a verified-safe claim — flag as untested if it matters for a specific install path.

## Priority 3 — reproducible `.pyz` builds

Real, current practice (reproducible-builds.org, drivendataorg/repro-zipfile, both fetched 2026-08-31): plain `zipfile.ZipFile` (which `zipapp` uses internally) stamps each entry with **current wall-clock mtime**, so two builds of an identical source tree at different times produce byte-different `.pyz` files. The fix pattern used across the ecosystem:
1. Set `SOURCE_DATE_EPOCH` in CI to a fixed integer Unix timestamp (commit date is the usual choice) — this is the cross-language convention reproducible-builds.org documents, and recent CPython `zipfile` versions read it directly for some operations.
2. Where the stdlib doesn't itself honor `SOURCE_DATE_EPOCH` for zip entry timestamps (it doesn't, universally, as of this CPython line — confirmed by the existence of the third-party `repro-zipfile` package specifically to patch this gap), normalize timestamps yourself: either monkeypatch/wrap `zipfile.ZipInfo.date_time` to a fixed tuple before calling `zipapp.create_archive`, or build the archive with `repro-zipfile`'s `ReproducibleZipFile` drop-in replacement and hand that off to `zipapp` (zipapp accepts either a directory or an already-built archive-like object depending on how it's invoked at the Python API level, not just the CLI).
3. Sort file iteration order deterministically (`os.walk`/`Path.rglob` order is filesystem-dependent) before adding entries — same-content-different-order still hashes differently.
4. Fixed default in the ecosystem convention: **1980-01-01 00:00 UTC**, the earliest timestamp the ZIP format supports, used when `SOURCE_DATE_EPOCH` is unset.

Given nox is explicitly zero-dependency, the practical choice is: don't pull in `repro-zipfile`; instead wrap `zipfile.ZipInfo` construction (a handful of lines) to force a fixed `date_time` and `external_attr`, iterate the source tree with `sorted()`, and set `SOURCE_DATE_EPOCH` in the release CI job for documentation/consistency with the wider ecosystem even though the stdlib path won't auto-read it everywhere.

### Negative (Priority 3)
- Did not verify which exact CPython version(s) added partial `SOURCE_DATE_EPOCH` support to `zipfile` — treat "recent zipfile reads it" as a general ecosystem claim (from the search results, tied to a NixOS packaging discussion and a 2025-era cpython issue), not a version-pinned fact. Test byte-identical output across two CI runs directly rather than trusting the env var alone.

## Priority 4 — stdlib sufficiency for process control

| Need | Stdlib idiom | Docs |
|---|---|---|
| Spawn a long-running child | `subprocess.Popen(argv, stdout=PIPE, stderr=STDOUT, text=True, bufsize=1)` | docs.python.org/3/library/subprocess.html |
| Read stdout incrementally without deadlock | **Merge stderr into stdout** (`stderr=subprocess.STDOUT`) so there is exactly one pipe, then `for line in proc.stdout: handle(line)` (or `.readline()` in a loop) in a **dedicated thread**. If stderr must stay separate, use **one thread per pipe** (`threading.Thread(target=drain, args=(proc.stdout, q))` / same for stderr) feeding a shared `queue.Queue` the main thread consumes — not `selectors`/`select`, which **do not support pipes on Windows** (confirmed: docs.python.org/3/library/selectors.html states pipes work on Unix but only sockets are supported on Windows). This is the actual cross-platform-safe idiom; `Popen.communicate()` is documented as deadlock-safe but blocks until process exit, so it cannot serve as a heartbeat/liveness signal for a long review run — it's right for "run and collect everything," wrong for "stream events as they arrive." | docs.python.org/3/library/subprocess.html#subprocess.Popen.communicate (deadlock warning), docs.python.org/3/library/selectors.html (Windows pipe limitation) |
| Enforce a wall-clock timeout | `proc.communicate(timeout=N)` catching `subprocess.TimeoutExpired`, or for the threaded-drain design, a `threading.Timer(N, proc.terminate)` / manual deadline check against `time.monotonic()` in the polling loop | docs.python.org/3/library/subprocess.html |
| SIGTERM→SIGKILL escalation | `proc.terminate()` (SIGTERM on POSIX, `TerminateProcess` on Windows) → `proc.wait(timeout=grace_seconds)` → on `TimeoutExpired`, `proc.kill()` (SIGKILL on POSIX; on Windows `kill()` and `terminate()` are the same call, since Windows has no SIGTERM equivalent — no graceful-shutdown signal exists there, only forceful process termination) → final `proc.wait()` | docs.python.org/3/library/subprocess.html#subprocess.Popen.terminate, `.kill()` |

`json`, `tomllib` (stdlib since 3.11, read-only — fine for nox reading a config/pyproject-style file, but it cannot *write* TOML, only parse), `shutil`, `dataclasses` all cover their obvious roles with no caveats worth flagging. `signal` is only needed directly if nox itself must catch SIGINT/SIGTERM to propagate a clean shutdown to its child (`signal.signal(signal.SIGTERM, handler)`) — the Popen-side termination above doesn't need it.

**Nothing in the four priorities requires a third-party package** for nox's process-control needs. The one place a third-party package (`repro-zipfile`) exists and is tempting is reproducible builds (Priority 3) — but it's small enough to reimplement in a few lines given the zero-dependency constraint, per the ponytail-style "stdlib does it, then don't add a dependency for six lines" reasoning; it's flagged only as prior art, not a recommendation to depend on it.

### Negative (Priority 4)
- `selectors` was not benchmarked/tested directly on Windows in this pass (no Windows environment available here) — the "pipes unsupported on Windows" claim is doc-sourced (docs.python.org), not independently reproduced, though it's an unambiguous, long-standing, well-known CPython platform limitation.
