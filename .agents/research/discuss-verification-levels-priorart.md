# Research: test levels and per-change test selection — prior art

## Metadata

Date: 2026-09-24
Lane: prior-art web scan
Discussion: .agents/discussions/verification-levels.md

## Direct answer

The literature and industry practice do not converge on one mechanism; they layer four independent, non-exclusive techniques:

1. **Named size/scope taxonomies** (Google small/medium/large/enormous; test pyramid/trophy/honeycomb; ISTQB unit/integration/system/acceptance) classify tests *statically*, at authoring time — they say what a test is, not what to run for a given change.
2. **Change/impact-based selection** (Microsoft TIA, Meta PTS, Google TAP, Ekstazi, Nx/Turborepo affected, pytest-testmon, Jest `--changedSince`) picks a *dynamic subset* of an existing suite per commit, based on dependency graphs or coverage history. All report large time/cost savings (2x–6x) with a small, non-zero, engineered-down miss rate, and all keep a slower full/periodic run as a backstop.
3. **Non-behavioural change classification** (CI path filters, docs-only skip) is a coarse, static, binary gate — cheap but has a well-documented failure mode: a required check that is path-filtered away never reports, so branch protection hangs. Fixes exist (job-level `if:`, an always-run no-op fallback) but are non-default and must be deliberately engineered.
4. **Result caching / memoization** (Bazel remote cache, Nx Cloud, Gradle build cache) skips re-running *already-executed identical* work — not a selection mechanism, a hashing-and-lookup one — with a well-documented correctness failure mode: undeclared inputs cause false-positive hits (stale artifact silently served), and naive caching of a flaky test's outcome cements a fluke as truth. Tooling has converged on runtime I/O sandboxing (Nx) or documented "don't cache tests" defaults (Bazel does not cache test *results* by default across machines the way it caches build actions) as the fix.

AI-coding-agent-specific evidence is thin but directionally consistent: giving an agent a **file→test dependency map (targeted context)** beats a **procedural "always run the tests" instruction** — one 2026 study (TDAD, arXiv:2603.17973) measured a 70% regression-rate drop (6.08%→1.82%) from graph-based targeted test selection, and found procedural TDD instructions alone made regressions *worse* (9.94%), attributed to context-window saturation and "regression laundering" (agents weakening assertions to turn tests green).

## Trends (trending / established / emerging / declining)

- **Established**: test pyramid (2009), Google test sizes (2010-2011), ISTQB levels (decades old, still the enterprise/QA-certification standard), Bazel/build-system dependency-graph affected-target selection (TAP, Nx, Turborepo), coverage-based RTS (Ekstazi, testmon).
- **Trending**: ML-driven predictive test selection (Meta PTS, 2018-2019, now widely cited/adopted pattern — commercial products like Launchable build on it); monorepo "affected" tooling (Nx, Turborepo) maturing task-level (not just package-level) granularity.
- **Emerging**: task/build sandboxing to make caching provably correct (Nx 22.7, 2026); AI-agent-specific test-selection research (TDAD, SWT-Bench-adjacent work) — this sub-area is <6 months old, thin evidence base, single-paper claims not yet independently replicated.
- **Declining / contested**: the test pyramid's fixed 70/20/10 shape is widely argued to be outdated for frontend/full-stack JS (testing trophy) and microservices (honeycomb) — the "one right shape" framing itself is declining in favor of "shape follows architecture."

## Key findings (each with a link)

- Google distinguishes test **size** (resource/runtime footprint: small = single process, medium = single machine, large = network-unrestricted, informally "enormous" = whole-system) from test **scope** (unit vs. integration vs. e2e) as two orthogonal axes — a common conflation the taxonomy explicitly warns against. [Software Engineering at Google, ch. 14](https://abseil.io/resources/swe-book/html/ch14.html), [Google Testing Blog: Test Sizes (2010)](https://testing.googleblog.com/2010/12/test-sizes.html)
- Test pyramid (Mike Cohn, 2009): many fast unit tests, fewer integration, few slow e2e, roughly 70/20/10. [Martin Fowler, "On the Diverse and Fantastical Shapes of Testing" (2021)](https://martinfowler.com/articles/2021-test-shapes.html)
- Testing Trophy (Kent C. Dodds, 2018) inverts the pyramid for frontend/full-stack JS: static analysis base, large integration-test middle, thin e2e cap. [baytechconsulting.com summary](https://www.baytechconsulting.com/blog/test-pyramid-vs-testing-trophy-whats-the-difference)
- Testing Honeycomb (Spotify) reweights toward integration tests for microservices, where per-service logic is thin but inter-service contracts are the risk surface. [Fowler, "Shapes of Testing"](https://martinfowler.com/articles/2021-test-shapes.html)
- ISTQB Foundation Level defines four test levels — component (unit), integration, system, acceptance — each with distinct objectives, independent of any specific tool or selection mechanism. [ISTQB Glossary](https://glossary.istqb.org/en/term/integration-testing-2)
- **Microsoft Test Impact Analysis (Azure Pipelines)**: uses static analysis of which methods a test exercises vs. which methods a commit touches; always re-includes previously-failing tests and newly-added tests; falls back to running the full suite when it cannot classify a change. Reported 50–80% CI test-time savings (Microsoft, Google, Datadog cited). [Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops), [Azure DevOps Blog](https://devblogs.microsoft.com/devops/accelerated-continuous-testing-with-test-impact-analysis-part-1/)
- **Meta Predictive Test Selection** (Machalica et al., ICSE-SEIP 2019, arXiv:1810.05286, published 2018/revised 2019 — >18 months old, foundational but not re-verified this cycle): ML model over historical outcomes + file-change statistics + dependency-graph distance; cuts total test-execution cost by ~2x (Facebook reported running only 33% of tests, catching 99.9% of regressions, cutting execution time 84%) while still surfacing >95% of individual test failures and >99.9% of faulty changes. Explicitly models test flakiness. [arXiv:1810.05286](https://arxiv.org/abs/1810.05286)
- **Google TAP**: builds a reverse dependency graph from BUILD files to compute "AFFECTED" test targets per changelist; large/slow tests still run, just asynchronously post-submit rather than pre-submit; evaluated on 500K+ commits, 5.5M+ targets, 4B+ target executions. [Assessing Transition-based Test Selection Algorithms at Google, ICSE-SEIP 2019](https://mpapad.github.io/publications/pdfs/ICSE-SEIP2019.pdf)
- **Ekstazi** (Gligoric et al., ISSTA 2015 — >18 months old): file-level *dynamic* dependency tracking (no VCS integration needed), 32% average end-to-end test-time reduction across 615 revisions of 32 OSS projects; adopted by real Apache projects. [Ekstazi paper (UT Austin PDF)](https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL15Ekstazi.pdf)
- **Nx affected** / **Turborepo `--filter`**: Nx builds a file-level project graph so affected-detection is per-file-import, not just per-package; Turborepo is package-level by default but has an opt-in task-inputs mode (`futureFlags.affectedUsingTaskInputs`) to get finer granularity. [Nx docs](https://nx.dev/docs/kb/nx-vs-turborepo)
- **pytest-testmon**: tracks *actual executed code per test* via coverage.py (not static imports), diffs against git changes, and is explicitly positioned as more accurate than import-graph tools because it isn't fooled by dynamic imports/DI/plugin coupling. **Jest `--changedSince`**: walks the *static* import graph — cheaper to compute, but acknowledged to miss dynamic-import and non-import dependencies. [pytest-testmon GitHub](https://github.com/tarpas/pytest-testmon), [til.masoodusmani.com on jest -o](https://til.masoodusmani.com/tils/jestchanged/)
- **GitHub Actions `paths-ignore` / required-checks pitfall**: a workflow skipped via `paths`/`paths-ignore` never posts a status for that commit; if it's a *required* check, the PR is stuck "Waiting for status to be reported" forever, since GitHub has no "skipped = passed" semantics at the workflow level. Fix: move the condition to job-level `if:` (a skipped job still reports success) or add a parallel always-run no-op workflow with the same check name. [GitHub Community Discussion #54877](https://github.com/orgs/community/discussions/54877), [GitHub Community Discussion #49124](https://github.com/orgs/community/discussions/49124)
- **Bazel caching**: correctness rests on the hermeticity assumption (identical declared inputs ⇒ identical outputs); undeclared inputs (untracked host tools, non-hermetic environment) silently produce cache poisoning/incorrect hits, and the ecosystem's fix is pinned/declared toolchains, not smarter caching. There is a known async-upload race where a previous failing test's output can get uploaded and mask a subsequent correct result. [bazelbuild/bazel #11057](https://github.com/bazelbuild/bazel/issues/11057), [Bazel remote cache debug docs](https://bazel.build/remote/cache-remote)
- **Gradle build cache**: "a valid cache key does not guarantee valid output" — missing/wrongly-declared inputs cause false cache hits; a single non-deterministic input (timestamp, absolute path, hostname) collapses the hit rate or produces wrong results. [Gradle: Solving common caching problems](https://docs.gradle.org/current/userguide/common_caching_problems.html)
- **Nx Cloud**: same false-positive-hit failure mode (missed input ⇒ stale artifact replayed); explicitly does **not** cache a flaky result — it detects pass/fail flip on identical inputs and retries rather than trusting either cached outcome; newest mitigation is runtime I/O sandboxing that fails a task if it reads/writes outside its declared inputs/outputs, closing the false-positive class structurally rather than by better declaration discipline. [Nx: Can You Trust Your Build Cache?](https://nx.dev/blog/can-you-trust-your-build-cache), [Nx: Detect and Retry Flaky Tasks](https://nx.dev/docs/features/ci-features/flaky-tasks)
- **AI-agent-specific (freshest, least-verified evidence)**: TDAD (arXiv:2603.17973, 2026) built an AST-based code↔test dependency graph and gave agents targeted "these tests are impacted" context instead of a procedural "run the tests" instruction; measured on SWE-bench Verified with two open-weight models. Regression rate: 6.08% baseline → 1.82% with graph-based targeted selection (−70%); a pure procedural-TDD-instruction condition *increased* regressions to 9.94%, attributed to context-window saturation ("full-suite tax") and agents weakening assertions to force green ("regression laundering"). Recommends keeping testing guidance under ~25 lines and giving "what to test" (a dependency hint) rather than "that you should test" (a blanket rule). [arXiv:2603.17973](https://arxiv.org/abs/2603.17973v2), [secondary write-up](https://thelgtm.dev/tdad-test-driven-agentic-development-reducing-code-regressions-by-70/)
- Anthropic's own guidance for Claude Code frames verification as agent-driven and evidence-based (run tests/build/lint, show output, iterate) but does not prescribe a level-selection policy — it leaves "what to run" to project-specific hooks/scripts. [Claude: Building verification loops in Claude Code with skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills), [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

## negative: (contradicting evidence, dead ends, reported failures of each approach)

- **Fixed small/full binary (option a)**: no direct negative evidence found, but the entire RTS/impact-analysis literature exists *because* "run everything vs. run nothing" was judged too coarse at scale (TAP paper: Google needed a third state between "run" and "skip" — AFFECTED vs. SKIPPED — precisely because binary didn't work at their commit volume).
- **Named levels config (option b)**: ISTQB/pyramid taxonomies classify tests, they don't by themselves decide *what to run when* — Fowler and others explicitly note the "one right shape" framing is contested (pyramid vs. trophy vs. honeycomb disagree by architecture), so a fixed named-level policy risks being wrong for the project's actual architecture if copied uncritically.
- **Change/impact-based selection (option c)** — the biggest source of counter-evidence:
  - RTS "has not been widely adopted in practice" despite being proposed 30+ years ago, per the Ekstazi paper's own framing — tooling friction, not algorithmic weakness, was the adoption blocker.
  - Static-import-graph selection (Jest `--changedSince`) is acknowledged to be **inaccurate** for dynamic imports, runtime config, and DI — a structural miss class, not an edge case.
  - Meta PTS explicitly trades away completeness: even its best mode only *guarantees* 99.9% of faulty changes reported, i.e., accepts a non-zero designed-in escape rate as the cost of the 2x savings; TIA/TAP-style tools all keep a slower full/periodic run specifically because none claims 100% recall.
  - Regression Test Selection false negatives are called out explicitly as the dangerous failure mode ("release silently-broken compositions to production") vs. false positives which "only inflate test cost" — the literature treats the two failure directions as asymmetric in severity, not equally bad.
  - Microsoft TIA is explicitly scoped-limited: "managed code and single machine topology" only — it falls back to full-suite for anything it can't analyze, which caps its applicability in polyglot/distributed systems.
- **Docs-only / non-behavioural skip (part of option c/d boundary)**: the required-check-never-reports failure is well documented and is a *hard* GitHub platform limitation, not a misconfiguration edge case — teams that adopt path-filtering on a required check hit it by default unless they know the job-level `if:` workaround in advance. A second reported misclassification failure: a PR that edits only `.github/workflows/**` can be *incorrectly* bucketed as "docs-only" by naive classifiers, skipping the one CI run that must validate the CI change itself.
- **Result caching (option d)**: every system surveyed (Bazel, Gradle, Nx) documents the same failure shape — an under-declared input set makes the cache key stable while the true output changes, so caching returns a *confidently wrong* stale result rather than failing loudly. Flaky tests compound this: naively caching a test's outcome cements a non-deterministic result as if it were deterministic truth; Nx's fix is to detect-and-retry rather than cache on flake, not to cache "more correctly."
- **AI-agent evidence caveat**: TDAD is a single paper, posted 2026 (very recent, un-replicated), evaluated only on two open-weight models over 100 and 25 SWE-bench instances respectively — a small sample. Its finding that procedural instructions actively *increase* regressions is the most surprising/least-corroborated claim in this whole survey and should be treated as a lead, not settled fact.

## leads: (one line each: lane name — reason)

- monorepo-tooling-deep-dive — Nx task-graph internals and Turborepo `affectedUsingTaskInputs` are new-ish (2026) and could give the toolkit a concrete file-level-affected implementation pattern to imitate.
- cache-correctness-design — sandboxed I/O verification (Nx 22.7) is the most structurally-sound answer found to option (d)'s correctness caveat; worth a design lane if result-caching is adopted.
- ai-agent-test-selection-followup — TDAD is thin evidence; a lane re-checking for replication/criticism in 3-6 months before leaning on its 70% number.
- required-check-semantics — GitHub Actions' skip-vs-required-check interaction is a hard platform constraint worth its own short design note if option (c)/(d) intersects with branch protection in this toolkit.
