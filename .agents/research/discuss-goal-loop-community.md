# Research: community practice for long /goal runs

## Metadata

**Date:** 2026-09-22
**Domain:** cli
**Triggered by:** pre-plan discussion on replacing hand-written `/goal` prompts with a reusable mechanism for chaining hex-architect → hex-plan → hex-execute → hex-review → hex-finalize autonomously; follow-up to `.agents/research/discuss-goal-loop-priorart.md` (official-docs pass — skim that first, not duplicated here)
**Expires:** 2027-03-22

## Direct Answer

Community practice splits cleanly by primitive. Blog-level guidance on `/goal` converges on **short, verifiable, multi-criteria conditions** ("tests pass AND lint clean AND CHANGELOG has an entry"), explicitly rejecting subjective language — but no source, including Anthropic's own docs, confirms embedding a slash-command/skill invocation inside the condition text works; it remains untested/undocumented in the wild too. Separately, a live, unresolved GitHub bug ([#93744](https://github.com/anthropics/claude-code/issues/93744)) shows the evaluator may not even see the condition text at all in some cases, not just "transcript-only" as a design choice but as an outright defect. External Ralph-Wiggum-style tooling (ralph-orchestrator, Specstride/wiggum) has independently converged on much harder "done" verification — nonce-bound verdicts, grounded re-reads of cited files, signature-tracked stall detection — because plain LLM self-report is explicitly called "unreliable" in that ecosystem. Reported pitfalls are broad and mostly still open as of Sept 2026: permission prompts silently blocking unattended runs (`--dangerously-skip-permissions` not fully suppressing prompts, Cloud Routines showing prompts despite being documented prompt-free, Auto-mode prompts that render nowhere), compaction erasing CLAUDE.md-level instructions well before the compaction limit, and cost/iteration blowup ($50-100+ per 50-iteration loop, echoed independently by two source families).

## Key Findings

### 1. How practitioners write `/goal` conditions

- Blog consensus (dailydoseofds, gaodalie.substack, jiridolejs.cz, bartlomiejkrupa.dev — all 2026 Anthropic-docs-adjacent explainers, not independent field reports) converges on a **4-part condition shape**: measurable end state + stated check (how Claude proves it) + constraints on what must not change + optional turn/time cap. Multi-criteria conditions are common in examples: `"all tests in test/auth pass and the lint step is clean"`.
- Explicit anti-pattern flagged repeatedly: subjective/vague language ("clean," "optimized," "better," "make it look good") — cited as producing either endless burn with no progress, or the evaluator hallucinating success because nothing concrete exists to check.
- External-state conditions are called out as unverifiable by design: "no dirty data in the production database" fails because the evaluator only reads the transcript, never calls tools itself — same constraint documented officially, echoed independently here.
- **Skill/slash-command invocation inside condition text**: no source — vendor docs, blogs, or GitHub issues — confirms or denies this working in practice. The `/goal` doc page is silent (per prior-art file); community write-ups only ever show plain natural-language conditions, never `/goal /some-skill "..."` as a literal example. This should be treated as **untested community territory**, not merely an unconfirmed doc gap.
- Practical guidance leans toward **short conditions**, not pasted mega-prompts, specifically because of the 4,000-char ceiling and because "over-engineering" — using `/goal` for simple single-turn tasks — is called out as a misuse. For genuinely large goals, the pattern shown is a short condition ("CHANGELOG.md has an entry for every PR merged this week") that references a deliverable/file by name, not one that dumps the full task spec inline — but this is inferred from example density, not a source stating the tradeoff directly.

### 2. Making the transcript-only evaluator judge "done" reliably

- Anthropic's own guidance (as reflected in the blog layer) is the evidence-in-condition pattern: phrase the condition so the check *itself* forces Claude to paste verifiable output ("`npm test` exit code is 0" → Claude must run and paste the result for the evaluator to see it). This is the only reliability mechanism `/goal` natively offers; there is no scripted-check option within `/goal` itself (that requires dropping to a custom Stop hook, per the prior-art file).
- External tooling built specifically to fix this gap goes considerably further than anything native to `/goal`:
  - **Specstride/wiggum** (proposer/critic/orchestrator pattern, [github.com/mairp/wiggum](https://github.com/mairp/wiggum)): critic verdicts must end in `VERDICT <nonce>: APPROVED|REJECTED` with a random per-call nonce parsed only from the critic's own reply — explicitly to stop a proposer from forging its own approval. Before judging, the critic does "a read-only grounding pass over cited files" (existence/size/freshness check) and appends that snapshot to the transcript, rather than trusting prose claims. Rejected evidence is archived before retry so stale evidence can't satisfy the next attempt.
  - **ralph-orchestrator** ([mikeyobrien.github.io/ralph-orchestrator/research](https://mikeyobrien.github.io/ralph-orchestrator/research/)) states plainly that "completion promises" via string-matching are "unreliable," and offers no evidence-block/checklist pattern of its own — iteration count and cost are its only real guardrails, which is notably weaker than Specstride's approach.
  - Net signal: the more mature the external orchestration project, the further it has moved from "ask the model if it's done" toward mechanical re-verification (grounded file reads, nonce binding, signature-tracked stall detection) — i.e., practitioners who've iterated on this longest do **not** trust transcript-only self-report, even with well-written conditions.

### 3. Reported pitfalls

- **Premature "met" / evaluator can't see the goal at all**: [anthropics/claude-code#93744](https://github.com/anthropics/claude-code/issues/93744) (opened 2026-09-11, still open, no maintainer response as of this research) — `/goal <instruction>` stores the condition only inside a `<command-args>` field on a `type: "user"` command-metadata record; no separate plain user-message record is created. The Stop-condition evaluator apparently can't read `<command-args>`, so it re-fires without ever confirming, and after repeated failures **declares the condition structurally unachievable and keeps looping anyway** — reported from an unattended overnight run with ~9 wasted interruptions. This is a materially different and more concerning failure than "vague condition confuses the evaluator" — it's the evaluator not receiving the condition at all in some invocation path.
- **Idle check-in cap of 3**: covered already in prior-art file (native mechanism); no independent community reports found quantifying how often the 3-check-in ceiling is actually hit in practice — treat the official mechanism as the only source on this specific number.
- **Runaway cost**: "$50-100+ in API credits" for a 50-iteration loop on a medium codebase is repeated near-verbatim across ralph-orchestrator's own docs and the futureagi/ralphloop.sh blog sources already in the prior-art file — same order-of-magnitude claim from at least two independent tool ecosystems, which raises confidence it's a real anecdote-level number, though still not vendor-published.
- **Compaction losing instructions**: multiple 2026 sources ([dev.to/whoffagents](https://dev.to/whoffagents/why-your-claude-code-sessions-keep-losing-context-and-how-to-fix-it-nia), [ianlpaterson.com](https://ianlpaterson.com/blog/stop-claude-code-from-lobotomizing-itself-mid-task/)) describe CLAUDE.md-level instructions losing effectiveness after repeated compaction rounds — framed as "a session that works for 30 minutes may start ignoring rules at minute 90, not because the rules disappeared but because they got summarized into oblivion." One source frames permission-boundary state itself as re-derived from the transcript on each check, so a stated boundary can silently vanish if compaction removes the message that established it — a sharper, more concrete version of "instructions get lost" than a vague quality-degradation claim.
- **Permission prompts breaking autonomy** — this is the most actively-reported live pitfall, with multiple open GitHub issues as of Sept 2026:
  - [#32559](https://github.com/anthropics/claude-code/issues/32559): `--dangerously-skip-permissions` reported not suppressing prompts on every command in some environments, despite the flag's documented contract.
  - [#94004](https://github.com/anthropics/claude-code/issues/94004): a permission "Allow" prompt appeared mid an **unattended Cloud Routine run** — directly contradicting the documented "no approval prompts during execution" contract for Routines (flagged as a leverage point in the prior-art file's "leads" section — this issue undercuts that lead's reliability).
  - [#94348](https://github.com/anthropics/claude-code/issues/94348): in Desktop Auto mode, a permission prompt that needs to render sometimes doesn't render anywhere in the UI — the call just hangs, then gets silently killed as "cancelled" on the next message. This is a silent-hang failure mode, worse than a visible blocking prompt because there's no signal to notice.
  - [#39346](https://github.com/anthropics/claude-code/issues/39346): even in `bypassPermissions` mode, `.claude/` write protection still blocks on every settings change requiring manual approval — relevant if an autonomous loop needs to touch its own hex/`.claude` config mid-run.
  - [#37913](https://github.com/anthropics/claude-code/issues/37913) is an open **feature request** (not yet shipped) for a configurable auto-deny timeout on stuck permission prompts — its existence itself confirms the community regards "prompt blocks forever with no timeout" as a live, currently-unaddressed gap.
- **Idle subagents**: no new independent evidence beyond the prior-art file's `tonoid/agent-loop` / `pi-herdr-agents` / `agent-parley` findings; this pass did not surface additional sources narrowing that gap.

### 4. Meta-orchestrator + sub-orchestrator hierarchies, parallel inner loops, review/fix round caps

- **ralph-orchestrator** demonstrates the coarsest form of parallelism: independent, non-nested Ralph loops run simultaneously ("6 repositories shipped in a single session" at a hackathon) rather than a formal parent/child orchestrator hierarchy. An open **feature request** ([mikeyobrien/ralph-orchestrator#210](https://github.com/mikeyobrien/ralph-orchestrator/issues/210)) asks for fan-out/fan-in ("Agent Waves") with splitter/aggregator primitives specifically because the current tool is "strictly sequential — one hat executes at a time," and the reporter names the gap directly: "there's no way to express 'split this work into pieces, process them in parallel, then combine the results.'" This is not yet built — it documents unmet demand, not a working pattern.
- **Specstride/wiggum** has the most concrete round-cap design found in this pass:
  - `MAX_REJECTS` (default 3) bounds proposer/critic retry rounds; exceeding it halts the orchestrator and "leaves everything on disk for a human" rather than looping indefinitely — directly matches this project's existing "review round cap two" doctrine in spirit (bounded rounds, human handoff on exhaustion), though Specstride defaults to 3 vs. this project's 2.
  - A **separate** counter, `SPECSTRIDE_PROPOSER_MAX_CAPS` (default 3), tracks budget-exhaustion kills distinctly from content-rejections — so a pass that simply ran out of budget doesn't consume the same limit as a pass that was substantively rejected. This is a cap-taxonomy distinction (why did it fail: budget vs. quality) not present in the simpler "N rounds then stop" designs seen elsewhere.
  - A stall-detection layer (diagnostician/accelerator) avoids blind full-phase retries: when a rejection repeats the same unmet-criteria signature, a one-shot diagnostician call classifies the gap as `CASE: GROUNDING` (evidence was truncated, work is actually done) vs. `CASE: REAL-GAP` (genuine work remains), and only on a real gap does a narrowed accelerator retry restricted to the cited files. Documented motivating case: "a full retry had spent 16 minutes re-deriving what turned out to be a two-file fix" — i.e., the pattern exists specifically to avoid wasting a whole round re-deriving already-correct work, a failure mode plausible in hex's own bounded-round-cap design if a fix-round re-plans from scratch each time rather than diffing against the prior rejection reason.
  - No hierarchical "meta-orchestrator dispatching sub-orchestrators" pattern was found described in Specstride's own docs beyond the single proposer/critic/orchestrator triad — no evidence it nests itself.

## negative:

- **No source confirms or denies `/goal <text>` executing an embedded skill/slash-command invocation.** This remains the single most load-bearing unknown for the arcana design question and this pass could not close it — neither official docs (per prior-art) nor any blog/GitHub source found treats it as a known behavior either way. Treat as **unverified — test directly** rather than inferred from either direction.
- Blog-level sources recommending condition shape (dailydoseofds, gaodalie.substack, jiridolejs.cz, bartlomiejkrupa.dev, findskill.ai, matthewswong.com) are largely Anthropic-docs paraphrase/explainer content published in 2026, not independent field reports from people who ran multi-day loops and are reporting back what happened — treat their "best practice" claims as restated vendor guidance, not empirical practitioner consensus.
- Reddit search for direct practitioner `/goal` experience threads returned nothing relevant — this pass found **no organic community discussion forum thread** (Reddit, HN specifically on `/goal`) matching the topic; all "community" evidence here is blog posts and GitHub issues, not forum discussion. The one HN thread found (`news.ycombinator.com/item?id=46785684`) is about a Ralph-loop demo cloning commercial software, not about `/goal` reliability or orchestration patterns specifically — not fetched for comment-level detail in this pass.
- `mikeyobrien.github.io/ralph-orchestrator/research/` gave only a WebFetch-summarized view (no direct page read), so nuance on iteration-count-by-complexity ("simple: 5-10, medium: 15-30, complex: 40-100") should be treated as approximate, sourced from that one project's own guidance rather than cross-validated.
- Issue #93744 is single-reporter, unconfirmed by maintainers, and only 11 days old as of this research (opened 2026-09-11) — treat the root cause (`<command-args>` not read by evaluator) as the reporter's diagnosis, not a confirmed Anthropic explanation.

## leads:

- **Test `/goal /some-skill "args"` directly before designing around it** — since no source resolves this, and it's central to the "shape (a) vs (b)" question from the prior-art file, a 5-minute empirical check (set a goal with a skill invocation, inspect the transcript the way #93744's reporter did via `~/.claude/projects/<project>/<session>.jsonl`) resolves more uncertainty than further research would.
- **Evidence-block / grounded-re-read pattern from Specstride** is a stronger done-detection design than anything `/goal` offers natively — worth considering for hex-execute's own review-fix loop (which already has a 2-round cap per existing project memory) as a way to distinguish "reviewer evidence was stale/truncated" from "real gap remains," directly addressing the wasted-full-retry failure mode Specstride's own docs cite.
- **[#93744](https://github.com/anthropics/claude-code/issues/93744) is worth watching, not acting on yet** — if arcana's design leans on `/goal` for the hex chain, this bug (evaluator not seeing the condition at all in some invocation path) is a harder blocker than "vague condition" and should gate any `/goal`-based design until resolved or reproduced/refuted locally.
- **Permission-prompt-blocks-unattended-run is the most concretely-reported live risk** of the four pitfall categories asked about — more open GitHub issues, more recent, more specific reproduction steps than compaction or idle-subagent reports. Any arcana design running multi-hour unattended should budget for this as the most likely actual failure point, not a theoretical one.
- **ralph-orchestrator's fan-out/fan-in feature request (#210)** documents that formal parallel-wave orchestration is *demanded* but not yet delivered in that ecosystem — arcana's own hex-execute (file-disjoint work packages in parallel git worktrees, per project CLAUDE.md) is further along on this specific axis than the most-cited external Ralph tooling; worth noting as a genuine differentiator rather than a gap to close by importing an external pattern.
