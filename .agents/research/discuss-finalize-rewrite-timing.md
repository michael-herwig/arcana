# Research: Who Rewrites Feature-Branch History, When, and With What Etiquette

## Metadata

**Date:** 2026-08-29
**Domain:** devops
**Triggered by:** /hex-discuss "finalize phase"
**Expires:** 2027-02-28

## Direct Answer

Five distinct models of rewrite timing exist across the primary sources
checked, not a spectrum of "how often you rebase" but different answers to
*when a rewrite is legitimate at all*: amend-in-place every round (Gerrit),
squash-once-at-the-end (Kubernetes/Node/Zephyr policy, Rust's bors-squash),
a fixup-then-single-rebase hybrid (Rust's fixup/autosquash convention),
never-rewrite-once-exposed (Linux kernel), and no-mutable-branch-to-rewrite
at all (PostgreSQL, kernel submission side). Bare GitHub Flow is a sixth,
weaker baseline: it has no rule, which is precisely why force-push etiquette
became a live pain point serious enough that Rust built bot tooling
(triagebot's range-diff poster) to compensate for what Gerrit and
mailing-list review get natively.

## Models of Rewrite Timing

| Model | Who rewrites, when | Example |
|---|---|---|
| Amend-in-place, every round | Author amends the *same* commit each round; the review tool (not a branch) tracks identity | Chromium/Gerrit |
| Squash-once-at-the-end | Commits accumulate additively during review; one squash event, at or after approval, often bot-driven | Kubernetes, Node.js, Zephyr (per discovery lane), Rust (`@bors squash`) |
| Fixup-then-single-rebase | Author pushes `fixup!` commits additively during review; one `rebase --autosquash` folds them, timing at author's discretion | Rust (`git.md` troubleshooting workflow) |
| Never-rewrite-once-exposed | Nobody rewrites a commit once others may have pulled it; only *reparenting* (moving the base) is allowed, and only with cause | Linux kernel |
| No mutable branch to rewrite | Each revision is a new, version-numbered artifact (email + patch file); nothing is force-pushed because nothing is shared-mutable | PostgreSQL, kernel patch submission |
| Ad hoc / no platform rule | GitHub Flow's own docs endorse pushing new commits through review; force-push is a team-adopted convention the platform doesn't natively support | Bare GitHub Flow |

### 1. Amend-in-place (Gerrit / Chromium)

A `Change-Id` footer — auto-generated by `git cl upload` — is Gerrit's
identity key for a logical change, independent of commit SHA. Every review
round is a `git commit --amend` + re-upload, producing a new "patchset"
under the same Change-Id rather than a new commit:

> "To upload new patch sets that address comments from the reviewers,
> simply commit more changes to your local branch and run `git cl upload`
> again."

Rebasing onto a newer base mid-review is permitted but must be *isolated*
from substantive changes — address review comments first, upload that as
one patchset, then rebase with "no other changes" as its own patchset:

> "This makes it easy for reviewers to see the changes made in response to
> their comments, and then quickly verify the diffs from the rebase."

Cost/benefit: reviewers get a clean, tool-generated patchset-to-patchset
diff automatically — no manual diff-of-diff needed. CI always builds one
commit per CL, trivially bisectable, with no ambiguity about which commit
is final. The cost is platform lock-in: the mechanism depends on Gerrit's
Change-Id tracking, not on plain Git.

### 2. Squash-once-at-the-end (Rust's bors path)

Rust's `rustc-dev-guide` treats squashing as an optional, deferred cleanup
step rather than an active review-time practice:

> "The easiest way to squash your commits in a PR on the `rust-lang/rust`
> repository is to use the `@bors squash` command in a comment on the PR."

By default the bot, not the author, does the folding: "[bors] combines all
commit messages of the PR into the squashed commit message." No merge
commits are accepted at all — "The rust-lang/rust repo uses what is known
as a 'rebase workflow.'" Combined with the discovery lane's findings on
Kubernetes (squash-to-one-commit-before-merge, bot-automated via
`tide/merge-method-squash`) and Node.js/Zephyr, this is the most common
model among GitHub-hosted projects: push additively during review, rewrite
exactly once, at or after approval.

Cost/benefit: reviewers watch an incremental, append-only history during
active review — nothing is ever force-pushed out from under an in-progress
read — while the *landed* history stays single-commit clean for
bisectability. The dependency is on bot tooling (bors, tide) to make the
final squash deterministic and to keep it from happening prematurely.

### 3. Fixup-then-single-rebase (Rust's manual convention)

The same guide separately documents a `fixup!`-commit convention for
correcting a specific earlier commit without disturbing history yet:

> "Tell git to commit the changes: `git commit --fixup <my-commit>`"
> followed later by "Squash your changes into the existing commits:
> `git rebase --autosquash -i upstream/main`"

This is additive-then-one-rewrite at the level of individual commits within
a PR, not just PR-vs-final: fixups accumulate visibly during review; the
interactive `--autosquash` rebase happens once, folding each fixup into its
target. Push safety for that one rewrite event is `--force-with-lease`,
recommended generally in the guide's standard workflow. The guide does not
state whether reviewers prefer this over squash-via-bors — it documents the
mechanism, not a review-etiquette rule about it.

### 4. Never-rewrite-once-exposed (Linux kernel)

The kernel's `rebasing-and-merging` doc draws the sharpest line of any
source checked, splitting "rebase" into two operations with different
legitimacy:

> **Reparenting**: "Changing the parent (starting) commit upon which a
> series of patches is built."
> **History modification**: "Changing the history of a set of patches by
> fixing (or deleting) broken commits, adding patches, adding tags to
> commit changelogs, or changing the order in which commits are applied."

The governing rule is exposure, not review status:

> "History that has been exposed to the world beyond your private system
> should usually not be changed. Others may have pulled a copy of your
> tree and built on it; modifying your tree will create pain for them."

A maintainer who pulls another developer's commits inherits an obligation,
not a license: "Do not rebase a branch that contains history created by
others. If you have pulled changes from another developer's repository,
you are now a custodian of their history. You should not change it."

Even the *allowed* operation (reparenting) is discouraged without cause —
"Just being on a newer base or avoiding a merge with an upstream repository
is not generally a good reason" — because it has a stated CI cost: "changes
the environment in which it was developed and, likely, invalidates much of
the testing that was done." This is the only source that names invalidated
testing as an explicit cost of rewriting, rather than a reviewer-visibility
cost.

Bisectability is the stated reason each patch in a series must build and
run on its own, independent of the rewrite-timing question but load-bearing
for why series get reworked *before* wide exposure: "Developers using
`git bisect` to track down a problem can end up splitting your patch series
at any point; they will not thank you if you introduce bugs in the middle."

### 5. No mutable branch to rewrite (PostgreSQL)

PostgreSQL has no long-lived PR branch to force-push into. A revision is a
new, explicitly version-numbered artifact:

> "Uniquely identify the new version. You can use `git format-patch -vN`,
> incrementing N each time; or you can add an incrementing numerical suffix
> manually."

Traceability across versions is manual and author-curated rather than
tool-generated: "Make sure it's easy to find any earlier discussion of the
patch, by providing Message-Id-based links to the mailing list posts."
Finalization is the committer's own act, not a branch state: "A committer
picks up the patch from the queue, and commits it." Git's own
`ReviewingGuidelines` (governing the Git project's own mailing-list
workflow, which PostgreSQL's model mirrors) formalizes the same
diff-of-diff need seen in Gerrit and GitHub, but solved by convention
instead of tooling — the cover letter is "where the changelog notes and
range-diff of subsequent versions are provided by the author," and an
explicit re-review handshake is expected: "After a series is rerolled in
response to your or others' review, make sure to re-review the updates."

Cost/benefit: no force-push footgun can exist because nothing shared is
mutable — every version is permanently archived and permalinked. The cost
is that the diff-of-diff is manual (author writes it into the cover letter)
rather than computed by the platform.

### Baseline: ad hoc GitHub Flow

GitHub's own `GitHub flow` guidance endorses pushing new commits
continuously through review — a non-destructive default with no stated
rewrite-timing rule at all. Teams that layer a force-push habit on top of
this (to keep history clean) hit a documented platform gap: GitHub's
compare view "only show[s] the most recent force-push diff. There's no way
to view the prior force-pushes," and inline comments lose their anchor
across a force-push. This gap is exactly why Rust's `triagebot` posts an
automatic `range-diff` comment "after such a scenario, which links to
triagebot `range-diff` feature" — bot-built compensation for a diff-of-diff
that Gerrit (patchset compare) and mailing-list review (cover-letter
range-diff) provide as part of the base model, not as an add-on.

## Key Findings

1. The five models split along one axis: whether a rewrite event happens
   continuously (Gerrit's every-round amend), exactly once at a chosen
   point (Rust/Kubernetes/Node squash-at-end, Rust's fixup-then-rebase), or
   never at all after first exposure (Linux kernel's reparenting-only
   rule) — versus PostgreSQL's orthogonal answer that there is no mutable
   artifact to rewrite in the first place.
   [rebasing-and-merging](https://docs.kernel.org/maintainer/rebasing-and-merging.html),
   [rustc-dev-guide git.md](https://github.com/rust-lang/rustc-dev-guide/blob/main/src/git.md),
   [Chromium contributing.md](https://chromium.googlesource.com/chromium/src/+/main/docs/contributing.md)
2. Only the Linux kernel names *invalidated CI/testing* as a stated cost of
   rewriting (reparenting "invalidates much of the testing that was done")
   — every other source frames rewrite cost purely in terms of reviewer
   diff-visibility, not build/test validity.
   [rebasing-and-merging](https://docs.kernel.org/maintainer/rebasing-and-merging.html)
3. Three independent mechanisms exist to solve the same "what changed since
   last review" problem, built by three different means: Gerrit does it via
   platform tooling (patchset compare, automatic), the kernel/PostgreSQL do
   it via human convention (cover-letter range-diff, author-authored), and
   Rust had to build a bot (triagebot) to retrofit it onto GitHub, which
   provides neither natively.
   [Chromium contributing.md](https://chromium.googlesource.com/chromium/src/+/main/docs/contributing.md),
   [git-scm ReviewingGuidelines](https://git-scm.com/docs/ReviewingGuidelines),
   [triagebot range-diff](https://forge.rust-lang.org/triagebot/range-diff.html)
4. Rust runs two rewrite-timing models simultaneously, not one: bot-driven
   squash-at-merge (`@bors squash`) for the PR-as-a-whole, and a manual
   fixup/autosquash convention for correcting an individual earlier commit
   without touching the rest of the series. The guide documents both
   mechanisms but does not state a review-etiquette preference between them.
   [rustc-dev-guide git.md](https://github.com/rust-lang/rustc-dev-guide/blob/main/src/git.md)
5. Gerrit's rebase etiquette explicitly separates *responding to review*
   from *moving the base* by requiring them as two separate patchsets even
   when both are needed in the same sitting — the only source that turns
   "don't mix a rewrite with a substantive change" into a structural
   requirement rather than a norm.
   [Chromium contributing.md](https://chromium.googlesource.com/chromium/src/+/main/docs/contributing.md)
6. The community pain that motivated Rust's triagebot range-diff feature is
   independently documented and still open on GitHub itself: force-push
   comparison in the native UI shows only the latest force-push's diff, and
   inline review comments lose their line anchor across a force-push.
   [community discussion #3478](https://github.com/orgs/community/discussions/3478)
