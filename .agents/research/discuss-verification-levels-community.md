# Research: narrowed test runs in practice — community

## Metadata
Date: 2026-09-24
Lane: community threads/blogs
Discussion: .agents/discussions/verification-levels.md

### Direct answer
Practitioners do run less than full suites per change — via CI path filters, dependency-graph "affected tests" (Bazel/Nx/Turborepo/Google TAP), and ML-based predictive test selection (Meta) — but every credible source pairs it with a safety net: a still-full run on the merge/main branch (merge queue, TAP's continuous run, Meta's guarantee floor), a documented fallback-to-full on ambiguous input (shallow clone, unparseable diff), and separate handling for flaky tests (quarantine, not selection). The most-repeated concrete failure mode is mechanical, not semantic: CI path filters (`paths-ignore`) combined with GitHub's branch-protection "required status checks" leave the PR permanently pending because a skipped workflow never reports — this is a known, currently-open class of issue, not a one-off.

### Key findings (each with a link)
- **Meta's predictive test selection (production, >1 year at time of writing)**: ML-ranked subset of the tests that transitively depend on the change; in production this "reduces total infrastructure cost of testing code changes by a factor of two, while guaranteeing over 95% of individual test failures and over 99.9% of faulty changes are still reported back to developers," and explicitly "accounts for test flakiness" in the model. [Engineering at Meta](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/) / [arXiv paper](https://arxiv.org/abs/1810.05286) — published 2018, ICSE-SEIP 2019 — **>18 months old**, treat as durable baseline not current state.
- **Google TAP (Test Automation Platform)**: builds a reverse-dependency graph from the build system's package graph; a change's "AFFECTED" targets are computed statically at build-graph granularity, and a target already validated at a later change in the queue is not re-run — this amortizes cost across overlapping changes rather than re-running per-commit. [Google TAP research paper](https://research.google.com/pubs/archive/45861.pdf) — dated, foundational description, no explicit recency marker (**flag as likely >18 months old**).
- **Azure DevOps Test Impact Analysis (TIA)**: selects impacted + previously-failing + newly-added tests; explicitly "for commits and scenarios that TIA cannot reason about, it will safely fall back to running all tests," and ships a config knob to force a full run at a set periodicity specifically to catch what selection misses. [Microsoft Learn — Test Impact Analysis](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops) — official docs, still current.
- **Nx / Turborepo `--affected`**: both use git-history + dependency-graph diffing; both tools document that an insufficient git checkout (shallow clone missing the base ref) causes them to fall back to treating everything as changed — a documented "safe but slow" failure mode rather than a silent gap. Verification tooling exists precisely because trust is the product: `nx graph --affected`, Bazel `rdeps`, and Turborepo's affected-package query let a team confirm the selector actually found everything before believing an "unaffected" verdict. (Aggregated from vendor-docs-based blog coverage, not a single primary source — see Sources.)
- **matklad, "Catch Flakes On Main" (May 2026)**: argues a merge queue that gates on a full run turns every subsequent main-branch failure into an unambiguous flake signal (not "bug or infra?") and recommends a public, easily-accessible dashboard of recent main failures to track and prioritize flake fixes; cites TigerBeetle's public DevHub dashboard as a working example. [matklad.github.io](https://matklad.github.io/2026/05/14/catch-flakes-on-main.html) — **recent, <18 months**.
- **HN discussion on "Faster CI with Selective Testing" (mill-build.org)**: commenter *deathanatos* states plainly that "path-based selection of tests, in every single CI system I have ever seen it implemented in, is wrong" and gives the concrete escape shape — sequential commits that each pass in isolation but fail together because the path filter can't see cross-cutting integration effects. Commenter *ay* details a real case of two independently-tested plugins (A and B) that each passed isolated test suites but broke when loaded together, due to memory-allocation/function-table-offset conflicts invisible to per-plugin selection. Commenter *lbriner* reports flaky tests are "maybe 50% of the failures" in their environment and that selective testing does nothing to address that root cause. Cost motivation cited by *lihaoyi* ($10–50 per PR update in CI spend) and *TypingOutBugs* (Windows GitHub runners at $0.54/minute). [HN thread](https://news.ycombinator.com/item?id=42517163) — dated via thread activity ("Dec 30"), year not confirmed in fetch — **treat as recent but unverified exact date**.
- **GitHub Actions `paths-ignore` + required status checks (ongoing, current)**: when a workflow is skipped entirely by path filtering, any job inside it configured as a required check gets stuck in permanent "Expected"/pending rather than reporting a pass — the opposite of the intended safety guarantee, since GitHub's own docs frame a required check as something that should run "under any circumstances." This is documented in GitHub's own troubleshooting docs and is a live, recurring community-discussion topic (multiple open discussions/issues), not a resolved one-off. Workaround pattern: filter at the *job* level (e.g. `dorny/paths-filter`) so the workflow itself always runs and reports "skipped" (counted as success) per job, rather than filtering the whole workflow with `paths-ignore`. [GitHub Docs — troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks), [community discussion #54877](https://github.com/orgs/community/discussions/54877), [community discussion #44086](https://github.com/orgs/community/discussions/44086) — **current, official + live community threads**.
- **Uber Go monorepo CI overhaul**: reports 69% build-time reduction (45min → 14min) and cross-service refactor time down from 6 weeks to 3 days after CI/build restructuring for their large Go monorepo (build-graph-aware CI, not purely path filters). [Uber Engineering blog](https://www.uber.com/en-AU/blog/how-we-halved-go-monorepo-ci-build-time/) — official, but exact publish date not confirmed in this pass.
- **Shopify Android monorepo**: pairs test retries with monorepo CI investment; pass rate went from 67% to 97% after addressing flakiness — presented as a flakiness-mitigation story (retries), not a coverage-narrowing one, but relevant to "how teams treat flaky tests under load." [Shopify Engineering](https://shopify.engineering/unreasonable-effectiveness-test-retries-android-monorepo-case-study)
- **Flaky-test quarantine as standard practice**: multiple sources describe the same shape independent of vendor — move a test failing intermittently above a threshold (~1–2% flake rate cited for Google-style thresholds) into a non-blocking quarantine lane with an owner and a deadline, rather than letting it gate merges or silently deleting/skipping it. Reported by secondary/vendor-blog sources for Google and Spotify (Spotify: flaky rate 4.5% → 0.4% in three months) — **these are vendor/content-marketing blogs (Trunk.io, Mergify, minware, talent500, tinycto, qaskills.sh) summarizing others' practices, not primary engineering-blog sources; treat the specific percentages as unverified**.

### negative: (failures, escapes, contradicting reports)
- **Path-based selection called categorically wrong by a practitioner**: deathanatos on HN — cross-commit/cross-module effects that individual-commit path diffing cannot see (see above). This directly contradicts a "diff the paths, skip the rest" design for anything with cross-cutting state.
- **Real integration escape from isolated-passing components**: the plugin A/B case above — the canonical "comment-only-shaped" failure isn't a comment at all, it's two changes that are each locally safe and provably wrong only in combination; selection-by-change-locality misses it by construction.
- **Bazel remote-cache correctness bugs** (primary source, official issue tracker, still relevant as a caching-hazard class even if the specific bugs are fixed/fixable):
  - A test's cache key doesn't include `--test_timeout`, so a test that previously passed under a longer timeout is served as a cached pass under a shorter one it would actually fail — a stale-cache false green. [bazelbuild/bazel #30576](https://github.com/bazelbuild/bazel/issues/30576)
  - A previously-failing test's result isn't cached, and can mask the correct (fixed) result on a later run under some cache configurations. [bazelbuild/bazel #11057](https://github.com/bazelbuild/bazel/issues/11057)
  - Tests tagged `no-cache` (meant to always run) were nonetheless served from cache, violating documented no-cache semantics. [bazelbuild/bazel #4680](https://github.com/bazelbuild/bazel/issues/4680)
  These are cache-key-correctness bugs specifically, not conceptual objections to caching — but they're the concrete shape of "test caching gave a wrong answer" that the discussion should worry about: cache keys must cover every input that affects pass/fail, or a config-only change (timeout, flag) can be invisibly absorbed into a stale hit.
- **GitHub `paths-ignore` required-check deadlock**: not a security/correctness escape but a process escape — a docs-only or otherwise-filtered PR can get permanently stuck (not merged) rather than incorrectly merged, because required checks never report. Net effect is the opposite direction (false block, not false pass), but it's the single most-repeated concrete incident shape across all searches this pass. See Sources.
- **Flaky tests are reported as a large fraction of CI noise independent of selection strategy**: lbriner on HN estimates ~50% of failures in their environment are flaky, and states selective testing doesn't touch this — i.e., narrowing what you run does not by itself solve the "is this failure real" problem; that needs separate flake-detection/quarantine machinery.
- **Low-confidence/unverifiable sources encountered and excluded from findings above**: several GitHub-issue search hits (orgs named `avatarsd-llc`, `attevon-llc`, `drydocs`, `FaultMaven`, `Netzbewegung-Backend`, `dflippojr`) look like auto-generated or extremely low-traffic/synthetic repos rather than established practitioner projects — cited nowhere else, no stars/context recoverable from search snippets. Not used as evidence above; flagging so they aren't mistaken for corroboration if re-surfaced. Similarly, several "flaky test quarantine" and "test impact analysis" summaries came from SEO/content-marketing sites (talent500.com, digia.tech, tinycto.tv, qaskills.sh, oneuptime.com, devopsboys.com, noopsschool.com) that restate vendor claims without attribution to a primary source — treat their specific numbers as unverified.

### leads: (one line each)
- **caching-key-completeness** — Bazel's timeout/no-cache bugs suggest the orchestration toolkit's own test-result cache (if any) needs an explicit audit of "what must be in the key," not just "what changed on disk."
- **cross-module/integration blind spot** — any per-file or per-package affected-test selection needs an explicit "these test suites always run regardless of diff" carve-out for integration/e2e suites, per the plugin A/B and deathanatos reports.
- **required-check semantics for skipped gates** — if the toolkit's own gates report as GitHub-style required checks, a "verification level N was skipped for this diff" must still emit a reporting status (success/skip), never silence, to avoid the paths-ignore deadlock class.
- **flake handling is orthogonal to level selection** — worth a dedicated design note: quarantine/retry policy is a separate axis from how much of the suite runs per gate.
