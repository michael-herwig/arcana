## Metadata

**Date:** 2026-09-23
**Domain:** cli / agent-config / observability
**Triggered by:** discussion `.agents/discussions/retro.md` — deep vendor pass
**Expires:** 2027-03-23 (fast-moving; several sources <2mo old already)

## Direct Answer

Every product surveyed still gates config-change proposals behind an explicit
human accept/edit/dismiss step (confirms the prior scan's finding — no
exceptions found). What's new in this pass: **Claude Code's `/insights`
(Feb 2026) is itself a working retro-shaped feature** — it mines 30 days of
local session transcripts, buckets friction into six fixed categories
(misunderstood request, wrong approach, buggy code, rejected action,
excessive changes, tool failures), and emits copy-paste CLAUDE.md rule text —
but it is manual-copy only, has no severity/frequency schema documented, and
does not attribute friction to a specific installed plugin or skill by
name/version. No product's data model carries skill/plugin attribution as a
first-class field. And on upstream-author feedback: one plugin author said it
outright — **plugins get zero usage/feedback telemetry from the host**, so
authors "have no idea how many users are using" their skill. Every proposal
loop found routes to *local* config (repo file, user profile, org
Knowledge base) — none routes a captured friction item back to the author of
the third-party skill/plugin/rule that caused it.

## Per-tool findings

### Claude Code — `/insights` (native) + auto-memory + plugin marketplace

- **Trigger:** manual invocation of `/insights`; separately, auto-memory
  writes during normal session use (per hex-priorart scan).
- **Stored fields:** report is a local HTML file
  (`~/.claude/usage-data/report.html`), generated by re-analyzing session
  transcripts with Opus; documented friction taxonomy has exactly six labels
  (misunderstood request / wrong approach / buggy code / rejected action /
  excessive changes / tool failures) with "concrete examples" attached per
  category — no published severity or frequency field, no schema doc found.
  [/insights overview](https://angelo-lima.fr/en/claude-code-insights-command/)
- **Approval UX:** none built in — output is "copy-paste-ready" CLAUDE.md
  rule blocks; the user manually selects and pastes. A third-party tool
  (`claude-insights`, community) adds a pipeline (parse HTML → filter →
  enrich → generate skills/rules/settings) with a manual-review mode
  (`CLAUDE.md-additions.md` staged for review) and a separate auto-apply mode
  that dedupes via 80%-word-overlap before merging — i.e. the ecosystem had
  to bolt on the review/gate step itself, native `/insights` doesn't ship one.
  [claude-insights repo](https://github.com/yahav10/claude-insights)
- **Scope:** local machine only, no team/org sync mentioned; "no external
  tracking — everything based on data already stored on your machine."
  [/insights overview](https://angelo-lima.fr/en/claude-code-insights-command/)
- **Attribution to plugin/skill:** not found. Neither `/insights` nor
  `claude-insights` links a friction item to the specific plugin/skill/MCP
  server active in that session; `claude-insights` maps friction *domains*
  (e.g. "testing," "CSS") to generically-generated new skills, not to
  existing installed ones.
- **Upstream-author channel:** none for `/insights` findings. Separately,
  Claude Code plugin marketplaces are plain GitHub repos — "reporting" a
  plugin problem means filing a GitHub issue on the plugin's own repo
  manually, no in-product routing.
  [Plugin marketplaces docs](https://code.claude.com/docs/en/plugin-marketplaces)
- **Marketplace feedback reality check:** the author of Superpowers (a
  752k-install Claude Code plugin) states plainly that **skills and plugins
  get no usage/feedback signal from the host at all** — "creators have no
  idea how many users are using" the plugin; the only loop is users manually
  forking the skills repo and opening a PR.
  [MindStudio Superpowers writeup](https://www.mindstudio.ai/blog/what-is-superpowers-plugin-claude-code)
- **Adjacent signal:** Claude Code does log a generic thumbs-style "How is
  Claude doing?" session survey event (`appeared`/`responded`), but this is
  product telemetry to Anthropic, not a structured friction record and not
  routed to any plugin author. [Monitoring docs](https://code.claude.com/docs/en/monitoring-usage)

### Cursor — background-model-proposed Memories + "generate rule from conversation"

- **Trigger:** a separate background model watches agent chats for durable
  facts (repeated corrections, stated preferences, project conventions) and
  proposes a memory; separately, a user can explicitly ask to "generate a
  rule" from the current conversation.
  [Cursor Memories guide](https://localskills.sh/blog/cursor-memories-guide)
- **Stored fields (Rules, the durable artifact):** `.mdc` frontmatter has
  exactly three fields — `description` (free text, used for agent-requested
  matching), `globs` (file-pattern scope), `alwaysApply` (boolean,
  always-on vs. conditionally injected). No severity/frequency/source field.
  [Cursor Rules docs](https://cursor.com/docs/rules)
- **Approval UX:** proposed memories surface for explicit approve/reject
  before persisting; toggle to enable/disable the whole proposal mechanism
  lives at Settings → Rules → "Generate Memories."
  [Cursor Memories guide](https://localskills.sh/blog/cursor-memories-guide)
- **Scope:** four activation modes map onto the frontmatter fields — Always
  Apply, Apply to Specific Files (glob), Apply Intelligently (description
  match), Apply Manually; separately Rules vs. Memories split as
  project-committed vs. more ephemeral. [Cursor Rules docs](https://cursor.com/docs/rules)
- **Attribution / upstream channel:** not found — Rules are plain repo files,
  no linkage to a specific installed extension/rule-pack version, no
  feedback-to-author path documented.

### Windsurf — Cascade auto-generated Memories

- **Trigger:** Cascade auto-generates a memory when it judges context
  "useful to remember" during a conversation; user can also explicitly say
  "create a memory of …". [Cascade Memories docs](https://docs.windsurf.com/windsurf/cascade/memories)
- **Stored fields:** not explicitly enumerated in docs beyond memory content;
  stored locally per-workspace at `~/.codeium/windsurf/memories/`.
- **Approval UX:** memories are created directly (no explicit accept/reject
  gate documented for the auto path, contrasting with Cursor/Devin) but are
  viewable/manageable/deletable after the fact via the Cascade panel — this
  is a **weaker gate** than Cursor's pre-save approval, worth flagging as a
  counter-example to "every product gates before write."
  [Cascade Memories docs](https://docs.windsurf.com/windsurf/cascade/memories)
- **Scope:** hard workspace isolation — memories from one workspace are not
  visible in another; no team/org sync mechanism found.
- **Attribution / upstream channel:** none found.

### Devin — Knowledge (mid-migration to "Skills in Plugins")

- **Trigger:** Devin suggests a Knowledge entry when session feedback implies
  something worth remembering.
- **Stored fields:** title, a natural-language **trigger description**
  (separate field governing *when* Devin recalls it — a retrieval-condition
  field, notable as more structured than most competitors), content (a few
  sentences), optional `!`-prefixed macro shortcut, per-user enabled/disabled
  toggle. [Devin Knowledge docs](https://docs.devin.ai/product-guides/knowledge)
- **Approval UX:** suggestion can be edited before saving, dismissed, or
  regenerated by giving Devin feedback on the draft (an iterate-in-place
  loop, not just binary accept/reject).
- **Scope:** organization (default, visible to org members) and enterprise
  (propagates across all orgs under a primary org); personal scope not
  documented as a Knowledge option. Knowledge can additionally be **pinned to
  specific repos** — the closest thing found anywhere to scoping a proposal
  by source-repo, though still not by skill/plugin identity.
  [Devin Knowledge docs](https://docs.devin.ai/product-guides/knowledge)
- **Structural note:** Knowledge is being deprecated in favor of "Skills in
  Plugins" — existing entries auto-convert into a knowledge-plugin per scope,
  folder structure preserved — i.e. Devin is collapsing "suggested knowledge"
  and "installed skill" into the same artifact type, which is directly
  relevant to whether a retro-proposed edit and an installed skill should
  share one schema. [Devin Knowledge docs](https://docs.devin.ai/product-guides/knowledge)
- **Attribution / upstream channel:** none found for third-party
  skills/plugins specifically.

### GitHub Copilot — custom instructions (coding agent) + code review instructions

- **Trigger:** the *first* time Copilot coding agent opens a PR in a repo
  with no instructions file, it leaves a **PR comment with a link to
  generate custom instructions** — proposal is surfaced inline in the
  artifact it just produced, not a separate report.
  [Copilot changelog: auto-generate custom instructions](https://github.blog/changelog/2025-08-06-copilot-coding-agent-automatically-generate-custom-instructions/)
- **Stored fields:** plain markdown files — `AGENTS.md`,
  `.github/copilot-instructions.md`, or scoped
  `.github/instructions/**.instructions.md` with an `excludeAgent` property
  letting an instruction block opt out of specific agents (code review vs.
  coding agent) — the one documented example of a *per-consumer scoping
  field* inside an instructions file. [Copilot changelog: agent-specific instructions](https://github.blog/changelog/2025-11-12-copilot-code-review-and-coding-agent-now-support-agent-specific-instructions/)
- **Approval UX:** generation happens on request (via the PR comment link or
  an explicit prompt); the result is a normal file diff/PR the human reviews
  and merges like any other change — approval UX is just ordinary code
  review, not a bespoke proposal card.
- **Scope:** repo-level; head-branch (not base-branch) read means an
  instructions edit can be tested in the same PR that motivated it — a
  tight propose→verify→land loop unique to this product.
  [Copilot repo instructions docs](https://docs.github.com/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)
- **Attribution / upstream channel:** none for third-party
  skills/extensions. Separately confirmed: Copilot's thumbs up/down telemetry
  goes to GitHub/Microsoft for model improvement and is **not exposed via
  public API to third-party extension authors** — direct evidence against
  any upstream-author feedback channel existing even where a rating UI does.
  [dev.to feedback-loop writeup](https://dev.to/devactivity/elevating-developer-quality-building-feedback-loops-for-your-vs-code-copilot-ai-agent-k32)

### OpenAI Codex CLI — AGENTS.md (static only)

- **Trigger:** none — Codex's memory model is explicitly static:
  `AGENTS.md` is hand-authored and read at session start; "hand-editing
  memories is not the supported path; updating an AGENTS.md file is,"
  i.e. there is no native suggest/propose loop at all, only manual editing.
  [Codex CLI cheat sheet](https://shipyard.build/blog/codex-cli-cheat-sheet/)
- **Approval UX:** N/A (no auto-proposal to approve); community add-ons
  (Hindsight, mem0-for-Codex) bolt on persistent/vector memory but sit
  outside the shipped product.
- **Scope:** repo-level file, standard precedence chain shared with other
  `AGENTS.md`-reading tools.
- **Attribution / upstream channel:** N/A — no proposal mechanism to route.

### Cline / Roo Code — Memory Bank

- **Trigger:** manual only — user issues "update memory bank"; Cline then
  reviews and rewrites the memory-bank files itself, no autonomous
  mid-session proposal.
  [Cline Memory Bank docs](https://docs.cline.bot/prompting/cline-memory-bank)
- **Stored fields:** a fixed small set of markdown files, not fields inside
  one schema — `projectbrief.md`, `activeContext.md`, `progress.md`,
  `decisionLog.md` (naming varies slightly Cline vs. Roo fork), each a
  free-text document rather than structured entries.
- **Approval UX:** the "update" is itself the write — no separate
  propose-then-approve step; the human's gate is simply choosing when to
  issue the update command and reviewing the resulting file diff afterward
  (git-diffable since files are repo-committed).
- **Scope:** project-local (`memory-bank/` folder in the repo).
- **Attribution / upstream channel:** none found.

### Amp — AGENT.md operational-learnings loop

- **Trigger:** described pattern is "every loop reads those files into the
  new context, does work, writes them back, and commits" — i.e. the agent
  itself both proposes and commits updates to `AGENT.md` as part of its
  normal task loop, the **weakest human gate found** in this survey (commit
  happens as part of the agent's own task, not a separate reviewed step,
  per the source description — flag as contested/thin, single blog source).
  [Nicolas Bustamante — Agent Memory Engineering](https://nicolasbustamante.com/blog/agent-memory-engineering)
- **Stored fields:** brief operational learnings (how to run the build,
  examples) — free text, no schema.
- **Approval UX / scope / attribution:** not independently corroborated
  beyond the one source; treat as a lead, not a settled data point — no
  official Amp docs fetched this pass.

### Kiro (AWS) — Steering files

- **Trigger:** auto-suggested on workspace open ("Kiro automatically
  generates a steering file recommended by Kiro based on the contents of the
  currently open workspace"); can also be manually authored.
  [Kiro Steering docs](https://kiro.dev/docs/steering/)
- **Stored fields:** markdown steering docs; in the AWS DevOps-agent
  reference architecture, steering additionally encodes explicit **scope
  constraints** as data — max files touched, no-new-files, no-new-deps,
  no-deletions, plus a protected-files list (buildspec, pipeline templates,
  steering files themselves) — the most explicit "blast-radius" schema found
  in this survey, though it's a remediation-agent guardrail pattern, not a
  friction-capture schema.
  [AWS DevOps Agent + Kiro CLI blog](https://aws.amazon.com/blogs/devops/automated-incident-remediation-with-aws-devops-agent-and-kiro-cli/)
- **Approval UX:** human reviews the resulting PR before deploy — gate is a
  normal PR review, not a bespoke proposal card.
- **Scope:** two explicit levels — global (all of a user's machine) and
  per-workspace, with workspace taking priority on conflict.
  [Steering timing/scope note](https://dev.to/aws-builders/aws-kiro-steering-application-timing-and-scope-verification-kiro-47gm)
- **Attribution / upstream channel:** none found.

### JetBrains Junie — guidelines.md

- **Trigger:** manual edit, or explicit user prompt asking Junie to explore
  the project and generate `guidelines.md` — no autonomous mid-session
  proposal found (closer to Codex's static model than Cursor/Devin's
  proactive one). [Junie guidelines docs](https://www.jetbrains.com/help/junie/customize-guidelines.html)
- **Approval UX:** generic action-level approval (Junie asks permission for
  commands/file ops/tool use as it works) — not a dedicated
  config-change-proposal flow; the generated `guidelines.md` itself lands as
  a normal file the user reviews like any Junie edit.
- **Scope:** project-level, version-controlled (`.junie/guidelines.md`).
- **Attribution / upstream channel:** none found.

## negative:

- **No product's stored-config schema has a skill/plugin/package +
  version attribution field.** Rules, memories, Knowledge entries, and
  steering files are uniformly either free-text or a small fixed set of
  scope/trigger fields (Cursor: description/globs/alwaysApply; Devin:
  title/trigger/content/macro); none of the eleven products surveyed (this
  pass + prior scan) records *which installed skill or plugin, at what
  version, produced this friction* as a first-class field.
- **No product ships a structured upstream-author feedback channel for
  third-party skills/plugins.** Confirmed twice independently: Copilot's
  thumbs-up/down telemetry is explicitly walled off from third-party
  extension authors ([dev.to](https://dev.to/devactivity/elevating-developer-quality-building-feedback-loops-for-your-vs-code-copilot-ai-agent-k32)),
  and a major Claude Code plugin author (Superpowers, 752k installs) states
  plugins receive **zero** usage/feedback signal from the host — the only
  loop is a user manually opening a GitHub PR against the skill's own repo.
  [MindStudio](https://www.mindstudio.ai/blog/what-is-superpowers-plugin-claude-code)
- **`/insights`, the closest native analog to the retro skill under design,
  ships with no approval gate at all** — it emits copy-paste text, not a
  reviewable proposal object; the community had to build a second tool
  (`claude-insights`) on top just to get a staged-review file and a dedup
  step. This is evidence *against* assuming "propose then gate" is free —
  Anthropic's own shipped feature skipped the gate and left it to the
  ecosystem.
- **Windsurf's auto-memory write is weaker than the "always gated" claim
  from the prior scan** — Cascade writes the memory directly when it judges
  it useful; the human control is post-hoc view/delete, not pre-write
  approval. This is a partial contradiction of the prior research file's
  "every product requires an explicit accept/dismiss" finding — Windsurf is
  the one counter-example found, and Amp's described loop (agent commits its
  own AGENT.md edits as part of the task) is a second, weaker-sourced one.
- **Devin's trigger-description field and Kiro's blast-radius constraints**
  are the two most structured schemas found, but neither is a "friction
  entry" schema — Devin's trigger field governs *retrieval*, not
  *diagnosis*, and Kiro's constraints govern *what an agent may touch*, not
  *why a friction was logged*. Neither is directly reusable as the friction-
  entry taxonomy; at best they're precedent that structured sub-fields
  beyond free text do ship in production.

## leads:

- **Devin's Knowledge → "Skills in Plugins" migration** — worth a follow-up
  read once it's further along; Devin is the one vendor actively merging
  "suggested config" and "installed skill" into a single artifact type,
  directly relevant to decision (2)'s routing question.
- **`claude-insights` (community tool) internals** — its "80%-word-overlap
  dedup" auto-apply mode and `--facets` team-attribution flag are worth
  reading the actual source for (not just docs), since it's the one
  artifact found that already tries to solve consolidation UX on top of a
  friction feed, i.e. closest existing reference implementation of the
  consolidation step itself (complementing `agent-retro` from the prior
  scan, which covers capture but not consolidation).
- **Amp's AGENT.md commit-in-loop pattern** — only one blog source found;
  worth verifying against Amp's own docs whether agent-authored AGENT.md
  writes really do land without a human review step, since if true it's the
  one real counter-example to "no product auto-applies."
- **VS Code extension marketplace rating/telemetry APIs** — not checked this
  pass; would settle whether *any* IDE-extension ecosystem (not just
  AI-coding-specific tools) has solved author-facing feedback routing that
  this survey's target vendors haven't.
