# Research: Design-Pattern Precedent for a Multi-Backend Harness Adapter (`nox`)

## Metadata

**Date:** 2026-08-31
**Axis:** design-pattern precedent
**Question:** For a zero-dependency Python library presenting one interface over structurally different AI-coding-harness backends (argv+streaming-JSON, BYOK multi-provider, JSON-RPC-over-stdio-with-broker, undocumented-exit-code argv), what does good precedent say about adapter shape, capability negotiation, heartbeat/liveness modeling, tri-state outcomes, subprocess-seam testing, and upward config resolution?
**Sources:** inline citations below (docs, GitHub source, PyPI); web search only, no repos cloned
**Expires:** 2027-02-28 (library-landscape research; re-check if any cited project has a major version bump or nox's own backend set changes)

## 1. Adapter/facade over heterogeneous backends in Python

**`typing.Protocol` vs ABC vs duck typing (2025-2026 consensus):** structural typing (`Protocol`) is favored at system *boundaries* — adapters, plugin points — because it keeps coupling low and doesn't force third-party or internal-but-distant implementations into an inheritance hierarchy; nominal typing (`ABC`) is favored when the library itself owns and enforces the hierarchy (runtime `TypeError` on missing abstract methods) [Stanza, "Protocols vs Abstract Base Classes"](https://www.stanza.dev/courses/python-architecture/protocols/python-architecture-protocols-vs-abc); [Medium, "Protocol vs ABC: Modernizing the Command Pattern"](https://medium.com/@tihomir.manushev/protocol-vs-abc-modernizing-the-command-pattern-b5e92fe23054). A common hybrid: an internal `ABC` for shared implementation across the adapters you ship, plus a public `Protocol` describing the contract so external/test code can satisfy it structurally without inheriting anything — relevant if nox wants a `Runner` seam that test doubles can satisfy without importing a base class.

**Real, well-regarded libraries abstracting several heterogeneous backends behind one interface**, ranked by structural similarity to nox's problem (one process/protocol per backend, registry + capability variance):

- **`fsspec`** (filesystem-spec) — the closest precedent. `AbstractFileSystem` is a template base class each backend (`s3fs`, `gcsfs`, local, http, memory, …) subclasses; a module-level **registry** (`fsspec/registry.py`) maps a protocol string (`"s3"`, `"gcs"`, `"file"`) to an implementation class. Two registration modes: (a) direct class registration via `register_implementation()`, used when the module is already imported; (b) a **deferred string path** (`"package.module.ClassName"`) stored in `known_implementations`, so the actual backend module is imported lazily, only when that protocol is actually requested — avoids importing every optional cloud SDK on startup. New backends register themselves via **setuptools entry points**, or by PR into `fsspec.registry.known_implementations` for inclusion by default [fsspec registry source](https://github.com/fsspec/filesystem_spec/blob/6233f315548b512ec379323f762b70764efeb92c/fsspec/registry.py); [fsspec developer docs](https://filesystem-spec.readthedocs.io/en/latest/developer.html). Directly transferable to nox: lazy import per-backend (don't import the OpenCode adapter's provider-plumbing until OpenCode is selected), and a registry keyed by a string discriminator rather than a big if/elif.

- **`keyring`** (jaraco/keyring) — closest precedent for **capability-driven backend *selection*** (as opposed to fsspec's explicit-protocol selection). `KeyringBackend` is an ABC; every concrete backend supplies a `priority` **classproperty** that must raise `RuntimeError` (with a message stating the cause) if the backend is unsuitable in the current environment (wrong OS, missing native lib, headless session, …) rather than returning a sentinel value. A `viable` classproperty is `True` iff evaluating `priority` doesn't raise; `get_viable_backends()` filters all registered subclasses down to the viable ones, then keyring picks the highest-priority viable backend automatically. Backend classes self-register into a `_classes` set via a custom `KeyringBackendMeta` metaclass at *class-definition* time (no explicit `register()` call needed), and third parties add backends purely via **entry points**, with zero changes to keyring itself [keyring docs](https://keyring.readthedocs.io/en/latest/); [keyring backend.py source, confirmed by direct fetch 2026-08-31](https://raw.githubusercontent.com/jaraco/keyring/main/keyring/backend.py). This "probe by raising, not by returning a bool" idiom is a strong candidate for how a nox adapter should declare *itself* unusable (e.g., OpenCode adapter raising when no BYOK key is configured) vs. how it should declare a *capability* absent (see §2 — those are different questions and keyring only answers the first).

- **`watchdog`** — precedent for **platform/runtime-conditioned backend dispatch with an explicit degraded fallback**. `Observer` is a factory that picks `InotifyObserver` (Linux), `FSEventsObserver` (macOS, preferred) or `KqueueObserver` (macOS/BSD, fallback), `WindowsApiObserver` (Windows) — and a `PollingObserver` usable everywhere as the last resort, explicitly needed on network filesystems (CIFS) where the platform's native mechanism silently doesn't fire [watchdog GitHub](https://github.com/gorakhargosh/watchdog); [watchdog observers docs](https://pythonhosted.org/watchdog/_modules/watchdog/observers.html). Maps onto nox's `Heartbeat.kind`: `Semantic` ≈ native OS event backend, `ByteActivity` ≈ polling-by-snapshot, `ProcessOnly` ≈ "we can't watch anything, only tell if the process object still exists" — watchdog's lesson is that the fallback tier must be a **first-class, always-available backend**, not an afterthought, because some environments (CIFS; here, some future undocumented-CLI backend) can only ever get the degraded tier.

- **`apprise`** — precedent for **flattening a large N of heterogeneous external services behind one call**, useful as a scale reference (150+ services) but *not* a strong precedent for capability typing: apprise's unified `notify()` call intentionally lowest-common-denominators everything to "send this message, optionally with an attachment/image," which is exactly the flattening nox's design explicitly rejects for `Heartbeat` and outcome tri-state [apprise GitHub](https://github.com/caronc/apprise); [Apprise docs](https://appriseit.com/library/). Worth citing as the anti-pattern nox is deliberately avoiding — cite it as "what LCD-flattening costs" in §2's failure-modes discussion.

- **`SQLAlchemy` dialects** — precedent for **multi-level subclassing to share behavior across a *family* of similar backends** without one backend's quirks leaking. A `Dialect` base is subclassed per-database (`PGDialect`), then subclassed again per-driver (`PGDialect_psycopg2`); DBAPIs that speak to several databases (pyodbc) get a mixin from `sqlalchemy.connectors` for the behavior common across that DBAPI regardless of target database [SQLAlchemy dialects docs](https://docs.sqlalchemy.org/en/20/dialects/); [AOSA vol. 2, SQLAlchemy chapter](https://aosabook.org/en/v2/sqlalchemy.html). Relevant if a future nox backend (e.g. Codex-family future variants) shares a JSON-RPC-over-stdio transport but differs in RPC method names — the mixin-for-shared-transport, subclass-for-shared-vendor pattern is exactly SQLAlchemy's answer to that shape.

- **`pluggy`** (the pytest/tox/devpi plugin engine) — precedent for a **hook-specification contract that some implementations legitimately skip**. `@hookspec` declares the call signature the host will invoke; `@hookimpl` marks a plugin function as fulfilling it. Hooks can be marked `optional=True`, and the plugin manager validates that any *provided* implementation matches the spec, but does not require every plugin to provide every hook [pluggy GitHub](https://github.com/pytest-dev/pluggy); [pytest hook-writing docs](https://docs.pytest.org/en/stable/how-to/writing_hook_functions.html). This is a second, more granular alternative to keyring's whole-backend viability gate: pluggy negotiates capability *per hook* rather than per backend. Worth flagging as a heavier-weight option nox is very unlikely to need (it pulls in a call-loop / firstresult machinery nox's "zero-dependency" constraint would reject), but the *shape* — declare the contract once, let conformance be partial and typed — is the right mental model for `Config`'s "normalized core + opaque passthrough" split already settled.

**Negative:** no library was found that combines all three of nox's needs (typed capability record + tri-state outcome + typed heartbeat fidelity) in one place; each pattern above is precedent for one facet, not a single off-the-shelf design to copy wholesale.

## 2. Capability negotiation

**LSP (Language Server Protocol)** is the strongest, most battle-tested precedent for typed, structural capability negotiation between two sides that may each support a different subset of features. At `initialize`, the client sends `ClientCapabilities` and the server replies with `ServerCapabilities` in `InitializeResult`; **a missing property is normatively defined as absence of that capability** (not an error, not "ask again") — e.g., "if the server doesn't advertise `completionProvider`, the client won't send completion requests" [LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/); [LSP 3.18 spec source](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.18/specification.md). Two refinements directly relevant to nox:
- **Dynamic registration** (`client/registerCapability` / `client/unregisterCapability`) lets a server announce a capability *after* the initial handshake, in reaction to config changes — a pattern nox likely doesn't need at v1 (backends are fixed for a session) but is the right escape hatch if a future backend's capabilities can change mid-session (e.g., a broker reconnect downgrading from streaming to non-streaming).
- **`ClientCapabilities.experimental`** is a deliberately untyped escape bucket so servers can ship features ahead of spec adoption without breaking typed clients — directly analogous to nox's "opaque per-harness passthrough" in `Config`; LSP's version of that idea is scoped specifically to *capabilities*, not general config, which is a useful narrower framing nox could borrow ("experimental capability keys" vs. "opaque config passthrough" as two distinct escape hatches with different blast radii).

**How callers are stopped from assuming an absent capability**: LSP's answer is structural — the field is `Optional[X]`/absent in the negotiated capability record, and clients are specified (not merely advised) to gate every capability-dependent request behind a check of that record. The **failure mode LSP prose repeatedly warns about** is a client sending a request the server never advertised support for and getting an undefined response — i.e., type-level absence is necessary but not sufficient; the calling code must actually branch on it, and nothing in LSP's design prevents a caller from skipping the check (it's convention + testing, not a compiler guarantee). For nox this argues for making the capability record's Python type genuinely awkward to ignore — e.g. requiring an explicit `.get()`-with-default or a `match` over a closed `Literal`/enum rather than a permissive `bool` attribute a caller can just read past.

**General "capability pattern" in OO API design** (DZone) frames this as: instead of a monolithic interface everyone must implement in full, callers ask "do you support capability X" via a typed lookup, and are required to null-check / branch on the result — cleaner than `isinstance`/`instanceof` checks or catching `UnsupportedOperationException`, because it makes the "maybe absent" case a first-class return rather than an exceptional control-flow path [DZone, "The Capability Pattern"](https://dzone.com/articles/the-capability-pattern-future-). This is essentially LSP's model restated in general OO terms, and reinforces that nox's typed capability record (rather than an exception-per-unsupported-call) is the mainstream choice.

**MCP (Model Context Protocol)** also does explicit handshake-time capability negotiation (flags like a resources "subscribe" capability, protocol version negotiated by the server comparing against the client's requested version) [apxml MCP capabilities chapter](https://apxml.com/courses/getting-started-model-context-protocol/chapter-1-architecture-and-fundamentals/capabilities-negotiation) — corroborates LSP's pattern in a second, more recent AI-tooling protocol, i.e. this is the converged industry answer for agent/tool protocols specifically, not just editor tooling.

**Failure modes reported across sources:** (1) LCD flattening — apprise's uniform `notify()` (§1) hides real per-service differences (attachments, formatting) behind one shape, which is fine for its problem (best-effort notification) but is exactly wrong for nox where a caller *needs* to know "can this backend stream" to choose a code path, not just get silently degraded output; (2) unchecked-absence — LSP's own spec text has to repeatedly remind implementers to check capabilities before using them, meaning the type system alone doesn't enforce it in TS/JSON-based LSP; a Python `Protocol`/`Literal`-typed capability record with no default "everything is off" bool field is more defensive than LSP's own JSON schema achieves.

## 3. Liveness/heartbeat for heterogeneous subprocesses

No single supervisor in the survey models "alive" identically across all its children — each converges on a **tiered fidelity model** matching nox's `Semantic | ByteActivity | ProcessOnly` split:

- **systemd `WatchdogSec`** is the highest-fidelity tier: the *service itself* calls `sd_notify("WATCHDOG=1")` on a schedule, and this must be tied to genuine internal progress (queue advancement, loop ticks) rather than sent unconditionally — sources explicitly warn that a naive unconditional heartbeat defeats the mechanism, because a service stuck in an infinite loop can still execute the notify call and falsely report itself alive [oneuptime, systemd RestartSec/WatchdogSec guide, 2026-03-02](https://oneuptime.com/blog/post/2026-03-02-configure-systemd-restartsec-watchdogsec-ubuntu/view); [Kestra blog on liveness/heartbeat mechanisms, 2024-04-22](https://kestra.io/blogs/2024-04-22-liveness-heartbeat). This is `Semantic` done right: the signal must be *tied to actual work*, not merely "process is scheduled."
- **supervisord** has no semantic heartbeat at all — it only tracks process-exists / `stopwaitsecs` before escalating to `SIGKILL` on shutdown [supervisord PR #199 discussion](https://github.com/Supervisor/supervisor/pull/199). This is nox's `ProcessOnly` tier: no visibility into whether the child is doing useful work, only whether the PID still exists.
- **Nx Cloud's CI heartbeat**: a background process pings a service every few seconds from within the job; losing pings is treated as "the main job died" even though the job's own process might still be technically running, and the system fails the run and tears down agents on missed pings [Nx Cloud heartbeat docs](https://nx.dev/docs/concepts/ci-concepts/heartbeat-and-manual-shutdown-handling). This is `ByteActivity`-shaped: a coarse, out-of-band "still doing something" signal rather than a structured semantic event.
- **GitHub Actions self-hosted runners**: known failure mode is the listener process getting OOM-killed *silently* — no crash log, no alert — with the documented mitigation being an external healthcheck cron restarting the service if it's been dead more than N minutes [devopsboys, self-hosted runner offline fix, 2026](https://devopsboys.com/blog/github-actions-self-hosted-runner-offline-fix-2026/). Reinforces that `ProcessOnly`-tier supervision needs its *own* timeout distinct from the semantic tiers, because absence of the OS process is the only signal available and it can be very delayed.
- **pytest-xdist**: a directly relevant negative case for what happens *without* a proper heartbeat model — xdist has no timeout for a hung/stuck worker by design (it originally detected only session crash via EOF on the transport), so a worker can spin forever without xdist noticing, and interaction with `pytest-timeout`'s own signal-vs-thread implementation is a known source of hangs precisely because the two layers don't agree on how liveness is observed [pytest-xdist #298](https://github.com/pytest-dev/pytest-xdist/issues/298); [pytest-timeout #72](https://github.com/pytest-dev/pytest-timeout/issues/72). Cite this as the cautionary tale: **timeout policy must be owned by the same layer that owns liveness classification**, not split across two libraries with different assumptions — directly relevant since nox's `Heartbeat.kind` determines what "no activity" even *means*, so the timeout policy per backend must be selected using that same `kind`, not a single global timeout applied uniformly.
- **LSP's `$/progress` / `workDoneProgress`** is the closest precedent to a *typed, semantic* per-operation liveness signal in an AI-tooling-adjacent protocol: begin/report/end notifications carry an optional human message and percentage, and if no percentage is given the client is told to assume indefinite/unbounded progress rather than treating silence as death [LSP 3.17 spec, workDoneProgress](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/); [lsp-devtools workDoneProgress docs](https://lsp-devtools.readthedocs.io/en/release/capabilities/window/progress.html). This maps closely onto nox's `Semantic` heartbeat kind for a backend (e.g. Claude Code's streaming JSON) that emits structured progress events, vs. a backend that only offers raw stdout byte flow (`ByteActivity`).

**Timeout-policy-per-backend, not global**: none of the surveyed supervisors use one timeout value across heterogeneous children; systemd's is per-unit (`WatchdogSec` in the unit file), keyring's viability check is per-backend, watchdog's polling interval is only used for the fallback tier. The consistent lesson: **the timeout value and the definition of "silence" must both be attributes of the specific adapter/backend, driven by its `Heartbeat.kind`, never a single constant applied across all backends.**

## 4. Tri-state / indeterminate results

- **C++ Boost `tribool`** is the canonical tri-state precedent: three states, `true`/`false`/`indeterminate`, where indeterminate explicitly means "may be true or false, we don't know" — and critically, `tribool` overloads boolean operators so that combining an indeterminate with anything **propagates indeterminacy** rather than silently coercing to `false` [Boost tribool tutorial](https://www.boost.org/doc/libs/latest/doc/html/tribool/tutorial.html). This is the sharpest statement found of the principle nox's design already commits to (never coerce indeterminate to success) — worth citing as the strongest prior articulation, even though it's C++ not Python.
- **Rust's `outcome` crate** generalizes `Result<T,E>` to a `Success | Mistake | Failure` triad, and supports *narrowing* an `Outcome<S,M,F>` down to a plain `Result` by eliminating one of the non-success states when a caller has handled it — explicitly framed as a way to expand a consumed API's error surface with fine-grained control without forcing every caller into a 3-way match immediately [outcome docs.rs](https://docs.rs/outcome-46f94afc-026f-5511-9d7e-7d1fd495fb5c/latest/outcome/). This is the best-found answer to "how is indeterminate surfaced without every caller having to handle three branches": provide a narrowing/collapse operation that a caller invokes *explicitly* (visible in the type, not implicit), rather than defaulting the API to two-state and bolting a third state on.
- **Python `result` package** (rust-like `Result[T,E]` = `Union[Ok[T], Err[E]]`) and **`dry-python/returns`** (`Result`, `Maybe`, `IO`, `IOResult`, `Future`/`FutureResult` containers, "Railway Oriented Programming") are the mainstream Python precedents for typed result containers, but both are **binary** (ok/err) by default — neither ships a built-in third "indeterminate" state [PyPI `result`](https://pypi.org/project/result/0.11.0rc1); [dry-python/returns GitHub](https://github.com/dry-python/returns); [returns railway docs](https://returns.readthedocs.io/en/latest/pages/railway.html). For nox this means: there is no ready-made Python library that already ships a `Result`-like tri-state; the honest options are (a) a small custom `Literal["ok","error","indeterminate"]` tag plus a payload, structurally similar to `returns.Result` but with a third arm, or (b) using `returns`' `Result[T, E]` where `E` is itself a union that includes an `Indeterminate` variant — but that re-introduces the "collapses to error-shaped" risk the design explicitly wants to avoid, since an `Indeterminate` nested inside `Err` invites callers to `except`/handle it identically to a real error.
- **Ergonomic cost, reported honestly**: every source pushing tri-state (tribool's operator overloading, outcome's narrowing) does so specifically *because* a plain 3-way discriminated union forces every call site to add a third branch or hit a type-checker error; the tradeoff mature designs make is to keep the *storage* type 3-armed (never collapse in the type) but provide one explicit, opt-in narrowing/coercion function so most call sites can stay 2-branch **after a deliberate decision point**, rather than 3-branching everywhere by default. This directly supports nox's design brief ("surfaces raw, never coerced to success") as the correct default, with the caveat that ergonomics will suffer unless nox also ships one narrowing helper (e.g. `.assume_ok_or_raise()` / `.treat_indeterminate_as(Error)`) for callers who've decided how they want to handle it.

**Negative:** no widely-used, well-regarded Python library was found shipping a first-class tri-state result type out of the box; nox would be introducing new (if small) surface area here, not adopting an existing dependency.

## 5. Testing subprocess-driving code

- **The seam pattern (fake `Runner` injected, real call isolated to one line)** is well-established but mostly appears as bespoke code in individual projects rather than as a single named pattern in the literature; the closest packaged precedents:
  - **`pytest-subprocess`** hooks `subprocess.Popen` itself (the base every other subprocess function funnels through) and lets tests `fp.register(...)` expected argv → fake stdout/stderr/returncode, without touching production code's call sites at all [pytest-subprocess usage docs](https://pytest-subprocess.readthedocs.io/en/latest/usage.html); [Simon Willison TIL, pytest-subprocess](https://til.simonwillison.net/pytest/pytest-subprocess). This is an alternative to hand-rolling a `Runner` seam: monkeypatch at the `Popen` layer globally rather than inject a `Runner` object — lower ceremony, but couples tests to the real `subprocess` call signature rather than to nox's own abstraction, so it's a weaker fit for nox's stated goal (test doubles inject via the `Runner` seam, not via monkeypatching stdlib).
  - **`testfixtures.popen`** (`MockPopen`) is the more precedent-matching approach: it explicitly frames itself as a *replaceable instance*, closer to dependency injection, where the caller controls what `Popen(...)` returns rather than patching the module globally [testfixtures Popen docs](https://testfixtures.readthedocs.io/en/latest/popen.html).
  - **`subprocrunner`** packages the "wrap `Popen` in a `SubprocessRunner` class" idea nox is already committed to as a small standalone library, confirming the pattern is recognized as generically useful rather than nox-specific [subprocrunner GitHub](https://github.com/thombashi/subprocrunner).
- **Recorded-fixture / VCR-style approaches**: well-established for HTTP (`vcrpy` records real interactions to a YAML "cassette" on first run, replays thereafter for fast/deterministic/offline tests; `pytest-recording` wraps this for pytest, defaulting to a `none` recording mode in CI to hard-block accidental live calls) [vcrpy docs](https://vcrpy.readthedocs.io/); [pytest-recording GitHub](https://github.com/kiwicom/pytest-recording). **No equivalent widely-adopted "VCR for subprocess" library was found** — the closest is the general "golden file" pattern (commit a known-good captured output, diff future runs against it, fail loudly on drift), which sources describe in VCR's own terms ("golden cassettes") but which for subprocess output would have to be hand-built (e.g. captured JSON-stream fixtures per backend, replayed through the fake `Runner`). This is a real gap nox will not find a drop-in dependency for.
- **Contract tests that run the real binary, skipped when absent**: the standard shape combines a custom pytest marker + a `--run-<X>` CLI flag registered in `conftest.py`, with tests skipped unless the flag is passed (Simon Willison documents exactly this for `--integration`; the equivalent `--runslow`/`pytest.mark.slow` pattern is the other common variant) [Simon Willison TIL, opt-in integration tests](https://til.simonwillison.net/pytest/only-run-integration); general pytest skip/marker guidance corroborates `pytest.skip()` calls gated on runtime conditions such as a missing binary, typically checked via `shutil.which()` at collection or test-body time [pytest docs, basic patterns](https://docs.pytest.org/en/stable/example/simple.html). For nox, the natural shape is: `@pytest.mark.contract` + `--run-contract` flag + a per-backend `skipif(shutil.which("claude") is None)` (or `opencode`, etc.) so the contract suite is a no-op on a machine without the harness installed, but runs for real in CI/dev machines that have it.
- **What mature projects say about false confidence in mocked subprocess tests**: this specific framing (explicit warnings about mock-subprocess false confidence) was not found as a distinct, citable source in this pass — the closest supporting evidence is indirect, via the VCR/golden-file rationale itself (recorded-real-interaction testing exists specifically *because* hand-written mocks drift from real service behavior over time) and via the standard integration-test-opt-in pattern's whole reason for existing (a pure-mock suite is deliberately supplemented, not replaced, by a real-binary-gated suite). Treat "mocks alone give false confidence" as a widely-held implicit norm evidenced by tooling that exists to counter it, not as a directly quoted claim from an authoritative source.

**Negative:** no subprocess-specific VCR-equivalent library found; no directly-quotable "mocked subprocess tests are false confidence" source found — both flagged above as unverified/inferred rather than sourced claims.

## 6. Config-file resolution

- **Upward search + stopping conditions**: the converged pattern across tools surveyed (Ruff, uv, Pyrefly) is: walk from CWD toward the filesystem root, stop at the **first** directory containing a recognized config file — even an empty `[tool.X]` table counts as "found," search does not continue upward past it and configs are not merged across levels by default [BSWEN, "How Ruff Config File Discovery Works," 2026-03-29](https://docs.bswen.com/blog/2026-03-29-ruff-config-discovery/); [Pyrefly configuration docs](https://pyrefly.org/en/docs/configuration/). Secondary stopping conditions seen: a hard max-depth cap (one implementation cited uses 20 levels) as a backstop against pathological directory nesting, and a filesystem-boundary check (comparing `stat().st_dev` across steps) to avoid walking onto a different mounted filesystem than the one the search started on.
- **uv's cautionary case**: an open issue describes config resolution "blowing up" when an unexpected `uv.toml`-named directory (not file) is encountered during upward traversal — cited as evidence that upward search must be robust to name collisions between what the tool expects (a file) and what it actually finds (e.g. a directory of the same name), not just to "config not found" [uv issue #7351](https://github.com/astral-sh/uv/issues/7351).
- **Repo-root detection**: none of the surveyed tools use a single universal signal; `.git` presence is a common heuristic stopping point for "repo root" specifically (distinct from "config found"), but is not treated as authoritative by tools that also support monorepos or nested projects — the *config file itself* being found is generally weighted above `.git` as the actual stop condition.
- **Precedence when multiple candidate files exist in the same directory** (e.g. both a dedicated tool config and a `pyproject.toml [tool.x]` table): not resolved in detail by this pass's sources beyond the general convention that a dedicated/explicit config file (e.g. `ruff.toml`) takes precedence over an embedded `pyproject.toml` table when both exist in the same directory — treat this as a common-but-not-universally-sourced convention rather than a hard rule confirmed for every tool surveyed.
- **Security consideration — reading config from a directory the user did not intend**: **`mise`'s trust model is the strongest, most directly applicable precedent.** Because mise config files can execute arbitrary code (`[env]` directives, hooks, tasks), mise gates on an explicit trust state per config path: on encountering an untrusted config it will prompt interactively, or in non-interactive contexts either skip the config or fail with an untrusted-config error rather than silently executing it [mise trust CLI docs](https://mise.jdx.dev/cli/trust.html); [mise paranoid mode docs](https://mise.jdx.dev/paranoid.html); [mise security advisory GHSA-436v-8fw5-4mj8](https://github.com/jdx/mise/security/advisories/GHSA-436v-8fw5-4mj8) (documents a real bypass where local settings skipped the trust check — evidence this is a genuinely exploitable class of bug, not a theoretical concern). Trust is normally a one-time per-file grant (`mise trust`); a stricter "paranoid" mode additionally hashes the file so any edit invalidates prior trust and re-prompts; global/system-level config paths are implicitly trusted and exempt. `trusted_config_paths` lets a user pre-authorize whole directory prefixes (e.g. `~/projects/work`) so every config under them is trusted without per-file prompts. **Directly applicable to nox**: if nox's upward config search can land on a config file outside a directory the invoking user actually intended to run in (e.g. a parent directory of a monorepo the current session didn't ask to trust, or a config an unrelated party placed in a shared workspace), the mise-shaped answer is an explicit trust gate — prompt or fail-closed non-interactively — *especially* for any config field that can act as code or arbitrary argv (nox's opaque per-harness passthrough is exactly this kind of field), not merely for structured/typed config values like `model` or `timeout` which are comparatively low-risk to read implicitly.

**Negative:** exact cross-tool precedence rules when a dedicated config file and an embedded `pyproject.toml` table coexist were not confirmed beyond general convention; treat as an open detail to verify against nox's own two candidate config file names if that ambiguity can actually arise.

## Summary of strongest transferable precedents

1. **Adapter shape**: `fsspec`'s registry (string-keyed, lazy-imported backends) + `keyring`'s "probe by raising RuntimeError, not by returning a sentinel" viability check are the two most directly reusable patterns for nox's per-backend adapter registration.
2. **Capability negotiation**: LSP's handshake-time typed capability record, with absence-means-unsupported and no default "everything on" state, is the converged, twice-validated (LSP + MCP) industry answer; the risk it doesn't solve — callers skipping the check — argues for making nox's capability type structurally awkward to ignore (closed `Literal`/enum, not a permissive bool).
3. **Heartbeat/liveness**: every supervisor surveyed ties timeout policy to *which* liveness tier is in play (systemd's semantic watchdog vs. supervisord's process-only vs. watchdog's polling fallback); pytest-xdist is the cautionary tale for what happens when timeout ownership and liveness-classification ownership are split across two layers that disagree.
4. **Tri-state**: Boost `tribool`'s indeterminate-propagates-through-operators and Rust `outcome`'s explicit-narrowing-only are the sharpest statements of "never silently collapse the third state"; no Python library ships this off the shelf, so nox is genuine (small) new surface area here.
5. **Subprocess testing seam**: `testfixtures.popen`/`subprocrunner` validate the injected-`Runner` shape nox has already chosen over `pytest-subprocess`'s global-monkeypatch alternative; no subprocess-VCR equivalent exists, so recorded-fixture testing for nox's backends will be hand-built, not borrowed.
6. **Config security**: `mise`'s trust-gate model, backed by a real CVE-class bypass, is the concrete precedent for treating nox's opaque per-harness passthrough config field as higher-risk than its typed core fields when resolved from a directory upward-search can reach without explicit user intent.
